검증 조건

테스트 버전
  • NVIDIA B300 SXM6 AC
  • Driver 580.159.03
  • CUDA 13.0
  • Ubuntu 24.04
환경
PCI Passthrough VM(vGPU Guest 아님) 위 Kubernetes, GPU Operator
검증 시점
2026-05
핵심 결론
Passthrough VM이라면 GRID 드라이버 없이 일반 드라이버만으로 B300의 MIG를 켤 수 있고, 서로 다른 프로파일을 섞는 Mixed 구성도 된다.

Blackwell 세대 B300에서도 앞선 글들처럼 MIG를 쓸 수 있는지 확인했다. 확인할 것은 GRID 드라이버가 따로 필요한지, 프로파일을 섞는 Mixed 전략이 되는지, 그리고 GPU Operator가 그 인스턴스를 Kubernetes 리소스로 알아보는지였다.

1. 검증 대상

  • GPU Passthrough 구성 여부
  • NVIDIA 드라이버 정상 동작
  • MIG 지원과 활성화
  • MIG Mixed 전략 적용 가능 여부
  • GRID 드라이버 필요 여부
  • Kubernetes GPU Operator 연계

2. 환경

항목 내용
GPU NVIDIA B300 SXM6 AC
Driver 580.159.03
CUDA 13.0
VM 유형 PCI Passthrough (vGPU Guest 아님)

nvidia-smi vgpu가 No supported devices in vGPU mode를 돌려줘서, 이 VM은 vGPU Guest가 아니라 물리 GPU가 직접 전달된 Passthrough 환경으로 판단했다.

3. GRID 드라이버는 필요한가

설치된 드라이버는 580.159.03이었고, vGPU Guest용인 nvidia-linux-grid-595를 설치해야 하는지 검토했다. 결론은 Passthrough 환경이므로 GRID 드라이버는 필요 없다였다. 현재 드라이버로 MIG를 쓸 수 있다.

4. MIG 활성화

활성화 전에는 Current: Disabled | Pending: Disabled다. GPU와 드라이버는 MIG를 인식하지만 꺼져 있는 상태다.

sudo nvidia-smi -mig 1
# Enabled MIG Mode for GPU 00000000:00:06.0

nvidia-smi에서 MIG M.이 Enabled로 바뀌었다. 별도 GRID 드라이버 없이 MIG가 켜졌다.

지원 프로파일

nvidia-smi mig -lgip로 조회한 GPU 인스턴스 프로파일이다.

5. Mixed 구성 만들기

서로 다른 프로파일 ID를 한 번에 지정해 인스턴스를 만들었다.

nvidia-smi mig -cgi 19,14,9 -C

1g.34gb, 2g.67gb, 3g.135gb가 한 GPU 안에 함께 생겼다.

GPU 0: NVIDIA B300 SXM6 AC
  MIG 3g.135gb    Device  0
  MIG 2g.67gb     Device  1
  MIG 1g.34gb     Device  2

Single과 Mixed

구분 Single Mixed (이번 검증)
프로파일 하나로만 (예: 1g × 7) 서로 다른 프로파일 혼합
GPU Operator strategy: single strategy: mixed
Kubernetes 리소스 예 nvidia.com/mig-1g.34gb=7 mig-1g.34gb=1, mig-2g.67gb=1, mig-3g.135gb=1

MIG Mixed와 vGPU Mixed는 다르다

이름이 비슷하지만 자르는 위치가 다르다.

항목 MIG Mixed (이번 환경) vGPU Mixed
분할 위치 VM 내부 하이퍼바이저
드라이버 일반 Data Center 드라이버 GRID 드라이버 + vGPU Manager
라이선스 GRID 불필요 NVIDIA vGPU 라이선스 필요
Kubernetes 연계 GPU Operator MIG 별도 vGPU 스택
용도 AI/ML 워크로드 여러 VM이 GPU 공유 
[MIG Mixed]   물리 GPU → Passthrough VM → MIG 1g / 2g / 3g
[vGPU Mixed]  물리 GPU → 하이퍼바이저 → VM1 / VM2 / VM3 (각각 vGPU 프로파일)

6. GPU Operator가 MIG 인스턴스를 인식하나

먼저 GPU Operator의 nvidia-device-plugin-daemonset, nvidia-mig-manager, nvidia-container-toolkit, gpu-feature-discovery가 정상인지 본다. 그다음 ClusterPolicy의 전략을 확인한다.

kubectl get clusterpolicy -o yaml | grep -A5 mig:
mig:
  strategy: mixed
migManager:
  config:
    default: all-disabled
    name: b300-mig-parted-config

노드 라벨에서 nvidia.com/mig.strategy=mixed가 보이면 정상이다.

kubectl get node gpu-node-1 --show-labels | grep -o 'nvidia.com/mig.strategy=mixed[^,]*'

Pod 할당 시험

프로파일마다 Pod를 하나씩 만들어 해당 리소스를 요청했다.

apiVersion: v1
kind: Pod
metadata:
  name: mig-1g-test
  namespace: gpu-test
spec:
  restartPolicy: Never
  containers:
  - name: cuda
    image: nvcr.io/nvidia/cuda:13.0.0-base-ubuntu24.04
    command: ["sleep","3600"]
    resources:
      limits:
        nvidia.com/mig-1g.34gb: 1

mig-2g-test는 nvidia.com/mig-2g.67gb, mig-3g-test는 nvidia.com/mig-3g.135gb를 요청한다. 세 Pod 모두 Running이 되었고 각 Pod 안의 nvidia-smi -L에서 요청한 크기의 MIG 디바이스가 보였다.

Pod 노드 GPU 타입 MIG
mig-1g-test gpu-node-1 B300 SXM6 AC 1g.34gb
mig-2g-test gpu-node-1 B300 SXM6 AC 2g.67gb
mig-3g-test gpu-node-2 B300X-3-135C 3g.135gb
