검증 조건

환경
Kubernetes(Kubespray), Loki Distributed(prometheus-stack)
검증 시점
2025-12
핵심 결론
원인은 Loki 설정이 아니라 kubelet clusterDNS의 잘못된 IP였다. kubelet 설정·systemd 인자·Pod 재생성이 모두 맞아야 풀린다.

Loki Distributed를 올렸더니 Compactor, Ingester, Distributor, Gateway가 한꺼번에 무너졌다. 처음에는 Loki 설정부터 의심했지만, 끝까지 따라가 보니 원인은 kubelet 설정 파일의 IP 한 줄이었다. 그 과정을 정리해 둔다.

Pod 주소와 이 클러스터의 kube-dns ClusterIP는 예시 값(10.0.0.x)으로 바꿨다. 10.233.0.3은 Kubespray 기본 cluster DNS Service IP라서 그대로 적는다.

배경과 증상

Loki Distributed 구성에서 다음 증상이 동시에 나타났다.

  • Compactor / Ingester / Distributor / Gateway Pod가 CrashLoopBackOff
  • memberlist 클러스터 join 실패
  • MinIO(S3) 접근 실패로 delete store 초기화 실패
  • Pod 안에서 DNS가 아예 동작하지 않음

증상은 여러 갈래였지만 로그를 하나씩 보니 전부 같은 곳을 가리키고 있었다.

memberlist join 실패

level=warn ts=2025-12-05T05:21:44.302145651Z caller=memberlist_client.go:595 msg="joining memberlist cluster: failed to reach any nodes" retries=0 err="1 error occurred:
        * Failed to resolve prometheus-stack-loki-distributed-memberlist: lookup prometheus-stack-loki-distributed-memberlist on 10.233.0.3:53: read udp 10.0.1.153:50418->10.233.0.3:53: i/o timeout
"

Compactor가 memberlist headless Service 이름을 DNS로 풀지 못했다. 그런데 질의를 보낸 대상인 10.233.0.3이 이 클러스터의 kube-dns ClusterIP와 달랐다. 이 주소는 CoreDNS Pod IP가 아니다. Kubespray 기본 cluster DNS Service IP이고, 서비스 CIDR 10.233.0.0/18에서 coredns/nodelocaldns Service에 붙는 ClusterIP다.

Compactor delete store 초기화 실패

failed to init delete store: failed to get s3 object: RequestError: send request failed
caused by: Get "http://prometheus-stack-minio.monitoring.svc.cluster.local:9000/k8s-loki/index/delete_requests/delete_requests.gz": dial tcp: lookup prometheus-stack-minio.monitoring.svc.cluster.local: no such host

S3 엔드포인트도 이름 해석에서 막혔다. memberlist만의 문제가 아니라 Pod 안 DNS 자체가 죽어 있다는 뜻이다.

Pod 안에서 DNS 직접 확인

kubectl exec -it prometheus-stack-loki-distributed-compactor-0 -n monitoring -- nslookup kube-dns.kube-system.svc.cluster.local

;; connection timed out; no servers could be reached

kube-dns조차 찾지 못했다. 클러스터 DNS 전체가 죽은 게 아니라 Pod에 주입된 DNS 설정이 잘못됐을 가능성이 커졌다.

resolv.conf

과거 구성

search monitoring.svc.cluster.local svc.cluster.local cluster.local openstacklocal
nameserver 10.233.0.3
options ndots:5
  • 들어가 있는 값: nameserver 10.233.0.3 (Kubespray 기본 cluster DNS Service IP)

현재 구성

  • 들어가야 할 값: nameserver 10.0.0.10 (이 클러스터의 kube-dns ClusterIP)

원인

Pod의 resolv.conf는 kubelet이 만들어 준다. 그리고 nameserver 값은 kubelet 설정의 clusterDNS에서 온다. 즉 kubelet clusterDNS가 처음부터 잘못된 IP로 들어가 있었다.

설치 로그를 다시 보니 이미 경고가 찍혀 있었다.

The recommended value for "clusterDNS" in "KubeletConfiguration" is: [10.0.0.10]; the provided value is: [10.233.0.3]

이 상태로 클러스터가 만들어졌으니 결과는 이렇게 이어진다.

  • 모든 Pod가 resolv.conf에 10.233.0.3을 nameserver로 갖는다.
  • 그 주소는 Kubespray 기본 cluster DNS Service IP라서, 서비스 CIDR이 다른 이 클러스터에서는 :53에 응답이 없고 계속 타임아웃이 난다.
  • Loki 컴포넌트의 DNS 기반 discovery가 전부 실패한다.
  • memberlist join이 100% 실패하고, Loki Distributed 전체가 무너진다.

영향 범위를 정리하면 다음과 같다.

기능 영향
memberlist gossip DNS를 풀지 못해 join 실패
Compactor delete store MinIO DNS 실패로 Compactor crash
Ingester ring memberlist 동기화 불가
Distributor ring ring 상태를 읽지 못함
Gateway nginx resolver LogQL 실행 실패
Querier store-gateway 조회 실패

Loki 쪽 설정을 아무리 만져도 풀리지 않는 문제였다.

조치

1. kubelet 설정 수정

모든 노드에서 kubelet 설정 파일을 연다.

sudo vi /var/lib/kubelet/config.yaml

clusterDNS를 kube-dns ClusterIP로 고친다.

clusterDNS:
- 10.0.0.10

kubelet을 systemd 인자(--cluster-dns)로 띄우는 환경이라면 그쪽 값도 같이 맞춰야 한다.

2. kubelet 재시작

영향 범위

해당 노드의 kubelet이 재시작되며, 그 순간 노드 위 Pod 상태 보고·볼륨 마운트 감시가 잠시 끊길 수 있다. 이미 떠 있는 컨테이너 자체는 보통 유지된다.

sudo systemctl daemon-reload
sudo systemctl restart kubelet

3. Pod 재생성

여기서 한 번 더 걸린다. 이미 떠 있는 Pod의 resolv.conf는 kubelet을 재시작해도 바뀌지 않는다. Pod를 새로 만들어야 한다.

영향 범위

monitoring 네임스페이스의 Loki Distributed Pod가 삭제·재생성되며, 재기동 동안 로그 수집·조회가 잠시 실패할 수 있다.

kubectl delete pod -n monitoring -l app.kubernetes.io/name=loki-distributed

또는 롤링 재시작을 한다.

영향 범위

지정한 StatefulSet/DaemonSet이 롤링 재시작되며, 해당 Pod가 차례로 내려갔다 올라오는 동안 짧은 요청 실패가 날 수 있다.

kubectl rollout restart statefulset -n monitoring prometheus-stack-loki-distributed-compactor
kubectl rollout restart daemonset -n monitoring prometheus-stack-loki-distributed-gateway

검증

임시 Pod로 DNS부터 확인했다.

kubectl run dns-check --image=busybox:1.36 -it --rm --restart=Never -- nslookup kubernetes.default

응답 서버가 kube-dns ClusterIP로 나오면 정상이다.

Server: 10.0.0.10

그다음 Compactor 로그에서 memberlist join과 S3 초기화가 통과하는 것을 확인했다.

msg="memberlist fast-join finished" joined_nodes=4
msg="S3 delete store initialized successfully"
msg="Starting compactor"

같은 Loki에서 만난 두 가지 설정 문제

DNS 문제를 풀고 나서 Loki Distributed 설정을 더 손보며 만난 문제가 둘 더 있었다. 둘 다 클러스터 DNS와는 무관한 Loki 차트 설정 문제라 이어서 적어 둔다.

Gateway(nginx)가 resolver에서 죽는 경우

Loki Distributed의 Gateway(nginx)가 CrashLoopBackOff에 빠지고 로그에 이런 오류가 찍혔다.

[emerg] 1#1: host not found in resolver "kube-dns.kube-system.svc.cluster.local" in /etc/nginx/nginx.conf:27
nginx: [emerg] host not found in resolver "kube-dns.kube-system.svc.cluster.local" in /etc/nginx/nginx.conf:27

values.yaml에서 resolver를 설정했을 때 나타났고, 차트는 loki-distributed, Loki는 2.7.x~2.9.x였다. 원인으로 짚은 것은 세 가지다.

  1. 세미콜론 중복. Helm 템플릿이 resolver 줄 끝에 ;를 자동으로 붙이는데, values에 이미 ;를 넣으면 nginx.conf에 ;;가 생겨 문법 오류가 된다.
  2. 끝 공백이나 줄바꿈. YAML에서 nginx.conf로 변환되는 동안 resolver 줄이 두 줄로 깨지거나 잘못 감싸이면 문법 오류가 된다.
  3. FQDN resolver. resolver kube-dns.kube-system.svc.cluster.local valid=10s;처럼 FQDN을 쓰면 nginx가 부팅 시점에 바로 DNS lookup을 한다. 응답이 지연되면 그 자리에서 실패해 CrashLoopBackOff가 된다.

해결은 resolver를 ClusterIP 기반 문자열로, 세미콜론 없이 넣는 것이었다. 먼저 kube-dns Service의 ClusterIP를 확인한다.

kubectl get svc -A | grep <CLUSTER_DNS_IP>
  nginxConfig:
    # -- Allows overriding the DNS resolver address nginx will use.
    resolver: "<CLUSTER_DNS_IP> valid=10s"

이렇게 고치자 nginx.conf가 정상으로 생성되고 Gateway Pod가 Running이 됐다. 정리하면 resolver는 따옴표로 감싼 문자열로 넣고 끝의 ;는 빼며, FQDN 대신 ClusterIP를 쓴다.

Compactor가 꺼져 있어 retention이 안 먹는 경우

모니터링 패키지의 Loki Distributed 구성을 보니 Compactor가 비활성화돼 있고 retention 관련 옵션도 빠져 있었다. Loki Distributed에서 retention을 적용하려면 Compactor가 필수라서, retention이 제대로 동작하지 않을 가능성이 있었다. 요구사항은 세 가지였다.

  • compactor.enabled: true로 켜고, 워크로드 kind는 StatefulSet을 유지한다.
  • 30일(720h) retention을 명시한다.
  • Compactor 이미지는 다른 Loki 컴포넌트와 같은 버전(2.9.10)으로 맞춘다.

values.yaml에서 바꾼 부분은 다음과 같다. 먼저 limits_config에 retention 기간을 추가한다.

loki:
  config:
    server:
      config: |
        limits_config:
          volume_enabled: true
          enforce_metric_name: false
          reject_old_samples: true
          reject_old_samples_max_age: 168h
          max_cache_freshness_per_query: 10m
          split_queries_by_interval: 15m
          retention_period: 720h   # 30일 retention

table_manager의 retention은 끄고, Compactor에서 retention을 켠다.

    table_manager:
      retention_deletes_enabled: false
      retention_period: 0s
    compactor:
      shared_store: s3
      working_directory: /var/loki/compactor
      compaction_interval: 10m
      retention_enabled: true
      retention_delete_delay: 2h
      delete_request_store: s3

스키마는 TSDB 기반으로 하나만 남기고 이전의 boltdb/boltdb-shipper 설정은 모두 지웠다.

    schemaConfig:
      configs:
        - from: 2024-01-01
          store: tsdb
          object_store: s3
          schema: v13
          index:
            prefix: index_
            period: 24h

마지막으로 Compactor 워크로드를 켠다.

compactor:
  kind: StatefulSet
  replicas: 1
  enabled: true

적용 뒤에는 세 가지를 확인한다.

  1. Compactor Pod가 생겼는지 본다: kubectl -n monitoring get pods | grep compa
  2. retention 설정이 반영됐는지 본다. Grafana의 Loki Runtime Config나 API로 확인한다.
curl -s http://<LOKI_ADDRESS>/loki/api/v1/status/config
  1. Compactor가 /var/loki/compactor를 기준으로 TSDB 블록을 병합·삭제하는지, S3 객체가 정상적으로 compaction되는지 본다.

정리

이번 장애는 Loki 설정 오류가 아니라 클러스터 전체의 kubelet DNS 설정 오류였다. 다음 세 가지가 모두 맞아야 완전히 풀린다.

  • 모든 노드의 kubelet config에 clusterDNS가 kube-dns ClusterIP로 들어가 있을 것
  • systemd 인자의 --cluster-dns도 같은 값일 것
  • Pod를 재생성해서 resolv.conf를 새로 받을 것

배운 점도 적어 둔다.

  • 여러 컴포넌트가 동시에 이름 해석에서 실패하면 애플리케이션보다 Pod의 resolv.conf를 먼저 본다.
  • nameserver가 이 클러스터의 cluster DNS Service IP가 아니면 그 자체로 이상 신호다. Kubespray 기본값 10.233.0.3이 다른 서비스 CIDR 위에 그대로 남아 있는 경우가 그렇다.
  • 설치 로그의 경고는 넘기지 말자. 답이 이미 거기 적혀 있었다.
