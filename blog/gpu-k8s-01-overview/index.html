검증 조건

환경
OpenStack VM 위 Kubernetes, NVIDIA A100 PCIe 40GB, Ubuntu 22.04
핵심 결론
GPU를 통째로 줄지, 시간으로 나눌지, 하드웨어로 쪼갤지에 따라 격리·활용률·모니터링 범위가 갈린다. 특히 Time-Slicing은 Pod별 GPU 사용량 메트릭을 얻을 수 없다.

사내 Kubernetes PaaS에 GPU 노드를 붙이면서 가장 먼저 한 일은 "Pod 하나에 GPU를 어떤 방식으로 줄 수 있고, 각각 무엇이 되고 안 되는지"를 직접 확인하는 것이었다. Passthrough, Time-Slicing, MIG, 그리고 이 둘을 겹친 구성까지 같은 A100 한 장으로 할당·수정·회수·모니터링을 시험했다. 이 글은 그 시험의 개요이고, 방식별 절차는 시리즈의 나머지 글에 나눠 적었다.

세 가지 방식

Passthrough: GPU 하나를 Pod 하나가 독점

GPU 한 장을 Pod 하나에 통째로 준다. 가장 단순하고 안정적이다. 다른 Pod와 GPU를 나누지 않으니 격리성이 좋고, Pod가 GPU 자원 전부를 쓸 수 있다. 연산량이 많고 오래 도는 딥러닝 학습에 맞는다.

Time-Slicing: 한 GPU를 시간 단위로 번갈아 사용

여러 Pod가 GPU 하나를 번갈아 쓴다. 활용률을 높이기 쉽지만, 같이 쓰는 Pod와 경쟁하는 상황에 따라 성능이 흔들린다. 실시간성이 낮은 추론 워크로드에 어울린다.

MIG(Multi-Instance GPU): 하드웨어로 쪼개기

A100 같은 GPU 한 장을 하드웨어 수준에서 여러 개의 가상 GPU로 나눈다. 인스턴스마다 메모리와 코어가 고정되고, 서로 완전히 격리된 독립 GPU처럼 동작한다. 크기가 다른 추론 워크로드를 안정적으로 병행 처리해야 할 때 쓴다.

방식 GPU를 나누는 단위 격리 어울리는 용도
Passthrough 나누지 않음 가장 높음 학습처럼 GPU를 오래 독점하는 작업
Time-Slicing 시간 낮음(메모리 공유) 실시간성이 낮은 추론
MIG 하드웨어 인스턴스 높음 크기가 다른 추론을 안정적으로 병행

시험 환경

VM 5대짜리 Kubernetes 클러스터에서 GPU는 워커 노드 한 대에만 붙였다. 컨트롤 플레인과 나머지 노드는 vCPU 4개, 메모리 8GB다.

항목 값
OS Ubuntu 22.04.3 LTS
GPU NVIDIA A100 PCIe 40GB (Ampere, GA100)
Compute Capability 8
메모리 40GB
MIG 최대 인스턴스 7

Pod 안에서는 TensorFlow JupyterLab 이미지와 gpu-burn을 부하 도구로 썼다. GPU를 쓰는 노드에는 NVIDIA 드라이버를 호스트에 직접 설치하고 GPU Operator를 올렸다. 설치 과정은 다음 글에 있다.

시험 항목과 결과

방식마다 같은 항목을 확인했다. 표의 O는 확인됨, X는 지원되지 않음이다.

Pod별 GPU 사용량 메트릭 O X O X

눈여겨볼 점은 마지막 줄이다. Time-Slicing이 들어간 구성은 Pod별 GPU 사용량을 메트릭으로 추적할 수 없다. 비활성화 시험에서는 설정을 끄기 전에 이미 할당된 자원이 그대로 유지되는 것도 확인했다.

노드를 재기동하면 기존 Pod는 UnexpectedAdmissionError로 남고 새 Pod가 만들어져 GPU를 다시 받는다. 남은 Pod는 직접 지워야 한다. 이 동작은 방식과 상관없이 같았다.

알아 둘 제약

  • vGPU는 GPU를 이미 한 번 나눈 것이라 그 위에 MIG를 다시 구성할 수 없다.
  • 한 VM에 vGPU와 Passthrough를 함께 할당할 수 없다. GPU를 제어하는 방식이 달라 서로 충돌한다.
  • vGPU를 쓰려면 NVIDIA 라이선스가 필요하다.
  • Time-Slicing은 GPU 메모리를 프로세스별로 격리하지 않고 공유한다. nvidia-smi나 DCGM에서도 전체 사용량만 보이고, 컨테이너나 VM 단위로 쪼개 볼 수 없다.
  • VM에서 MIG를 구성하면 VM 안에서 GPU 사용률(GPU Util)이 지원되지 않는다. Passthrough VM에서는 사용률도 보인다.
