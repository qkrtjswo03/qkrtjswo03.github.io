검증 조건

테스트 버전
  • management-monitoring / business-monitoring Helm 차트(메트릭·로그 구성, 트레이싱 확장 구성)
  • kube-prometheus-stack 66.4.0
  • helm upgrade --install prometheus-stack -n monitoring
환경
Kubernetes 멀티 클러스터(매니지먼트, 비즈니스), 사설 레지스트리와 StorageClass 필요
검증 시점
2025년
핵심 결론
이미지를 준비한 뒤 매니지먼트 클러스터를 먼저 설치하고, 비즈니스 클러스터는 매니지먼트 클러스터 S3 엔드포인트를 넣은 다음 설치한다. Query stores에 비즈니스 클러스터 Sidecar를 등록한 뒤 Grafana에서 thanos와 loki를 확인하고, 트레이싱 확장 구성에서는 Tempo 데이터소스(`http://<tempo-query-frontend-host>:3100`)도 Test한다. 네임스페이스·PVC·CRD는 uninstall로 지워지지 않는다.

앞 글까지 구성 요소를 나눴다. 이 글은 설치 순서와 값 점검, 메트릭·로그 구성 → 트레이싱 확장 구성에서 달라지는 점, 확인 명령과 자주 보는 문제를 모은다. 헬퍼 스크립트 이름(install.sh, uninstall.sh, scripts/apply-env.py)은 차트 묶음에 들어 있는 것을 기준으로 하되, 같은 동작은 helm upgrade --install으로도 수행할 수 있다. 메트릭·로그 구성과 트레이싱 확장 구성의 설치/삭제 스크립트는 버전 주석만 다르고 동작은 같다.

사전 요구

구분 요구사항
클러스터 Kubernetes 두 세트(매니지먼트, 비즈니스). 한 클러스터에는 두 차트 중 하나만 설치한다
도구 helm, kubectl, python3. 오프라인 이미지 로드를 쓰면 nerdctl(containerd), sshpass
레지스트리 registry.example.com:50000. containerd insecure registry(hosts.toml) 설정이 필요할 수 있다
스토리지 StorageClass. values 기본 예는 local-path, 가이드 체크리스트 예는 nfs-csi
etcd 메트릭 플랫폼 구성 요소를 쓰면 kubeEtcd.endpoints에 마스터 주소
노드 라벨 node=infra, example.io/monitoring-ha=true, example.io/monitoring-single=true
시간 전 노드 NTP 동기화. 어긋나면 Grafana 단기 구간이 No data가 된다

도구의 최소 버전은 차트 문서에 명시되어 있지 않다. 오프라인용 이미지 tar는 공개 설명만으로는 포함되지 않고, 원본 묶음 용량은 메트릭·로그 구성 약 2.1GB, 트레이싱 확장 구성 약 2.2GB로 적혀 있다. pull_images.sh 목록과 values 이미지 태그는 차이가 있을 수 있어, 설치 전에 values 기준 이미지가 레지스트리에 있는지를 본다. 메트릭·로그 구성 예로는 비즈니스 클러스터 목록에 주석 처리된 Promtail·python:3.11-alpine, 매니지먼트 클러스터 목록에 Operator v0.78.2 / Prometheus v2.55.1 같은 이전 태그가 함께 있을 수 있다.

설치 순서

  1. 매니지먼트·비즈니스 각 클러스터 노드에 이미지를 준비한다.
  2. 매니지먼트 클러스터: 노드 라벨, s3-key.yaml과 values를 확인한 뒤 차트를 설치한다.
  3. 비즈니스 클러스터: s3-key.yaml에 매니지먼트 클러스터 SeaweedFS S3 엔드포인트(<MANAGEMENT-VIP>:30333)를 넣고 설치한다.
  4. 매니지먼트 클러스터 Thanos Query stores에 비즈니스 클러스터 Sidecar(<BUSINESS-NodeIP>:10901)가 있는지 확인하고, 바뀌었으면 매니지먼트 차트를 다시 적용한다.
  5. 매니지먼트 클러스터 Grafana에서 Loki 데이터소스와 대시보드를 확인하고, 트레이싱 확장 구성에서는 Tempo 데이터소스(http://<tempo-query-frontend-host>:3100)도 연결해 Test한다.

헬퍼 스크립트를 쓰면 설치 전에 클러스터별 값을 물어 values와 s3-key.yaml, (매니지먼트 클러스터) kube-prometheus-stack values를 고치고 .bak을 남긴다. 매니지먼트 클러스터에서 받는 값은 Grafana domain, externalLabels.cluster, StorageClass, SeaweedFS S3 endpoint, etcd endpoints, Thanos Query 외부 store, 대시보드 언어(ko/en)다. 비즈니스 클러스터는 cluster 이름(externalLabels.cluster, Alloy CLUSTER_NAME), StorageClass, 매니지먼트 클러스터 S3 endpoint, etcd endpoints다. 대시보드 언어를 en으로 고르면 각 폴더의 en/*.json 존재 여부를 검사한다.

설치 전에 helm list로 같은 릴리스 이름의 차트 종류를 본다. 매니지먼트 클러스터와 비즈니스 클러스터는 릴리스 이름이 같아서, 한 클러스터에 다른 쪽 차트가 이미 있으면 중단한다.

helm upgrade --install prometheus-stack <차트경로> \
  -n monitoring --create-namespace --timeout 20m --wait
kubectl get pods -n monitoring

네임스페이스·릴리스·타임아웃 기본값은 monitoring, prometheus-stack, 20m이다.

바꿔야 하는 값

자격 증명과 주소는 자리표시자로 둔다. 하위 차트 README나 템플릿에 남은 <CHANGE_ME>는 예시·기본값이고, 운영 시에는 상위 values와 s3-key.yaml을 먼저 채운다. 시크릿이 포함된 채로 배포되거나 공유된 적이 있다면 그 자격 증명은 교체한다.

공통으로 손보는 항목은 Grafana domain / root_url(grafana.example.com), adminPassword, StorageClass, Prometheus externalLabels.cluster, kubeEtcd.endpoints, Thanos·Loki·(v4) Tempo S3 키와 엔드포인트, 레지스트리 호스트(registry.example.com:50000), Ingress/웹훅/VirtualService 호스트(*.example.com), Query stores의 비즈니스 클러스터 Sidecar, 대시보드 샘플 IP 자리표시자다.

트레이싱 확장 구성에서 NodePort를 앞단 HAProxy로 묶는 예시는 다음과 같다. listen 이름은 일반화했고, 구 가이드의 MinIO API 포트는 SeaweedFS S3 NodePort 30333으로 바뀌었다. 반영은 systemctl restart haproxy다.

listen ingress-management
    bind *:443
    mode tcp
    server management-master <INTERNAL_IP>:30443 check inter 2000 rise 2 fall 5

listen ingress-business
    bind *:443
    mode tcp
    server business-master <INTERNAL_IP>:30515 check inter 2000 rise 2 fall 5

listen seaweedfs-s3
    bind *:30333
    mode tcp
    server master-01 <INTERNAL_IP_01>:30333 check inter 2000 rise 2 fall 5
    server master-02 <INTERNAL_IP_02>:30333 check inter 2000 rise 2 fall 5
    server master-03 <INTERNAL_IP_03>:30333 check inter 2000 rise 2 fall 5

Control plane 메트릭을 모으려면 kubeEtcd.endpoints와 같은 주소로 각 구성 요소 메트릭을 연다. etcd는 --listen-metrics-urls=http://<MasterIP>:2381, kube-controller-manager와 kube-scheduler는 static Pod의 --bind-address=<MasterIP>(probe host와 동일), kube-proxy는 ConfigMap kube-system/kube-proxy의 metricsBindAddress를 모든 인터페이스의 10249 포트로 연다. 메트릭·로그 구성 문서에는 이 절차와 HAProxy 예시가 없고, 관련 values(예: kubeEtcd.endpoints)는 있으므로 트레이싱 확장 구성 설명을 참고하되 적용 여부는 환경에서 확인한다.

메트릭·로그 구성과 트레이싱 확장 구성의 차이

항목 메트릭·로그 구성 트레이싱 확장 구성
비즈니스 클러스터 추가 차트 — cert-manager, tempo-distributed, opentelemetry-operator(+ Collector / 대기 Job, CRD 4종)
신호 메트릭 · 로그 메트릭 · 로그 · 트레이스
Alloy v1.10.1 v1.16.3, clustering, Kubernetes Events, toleration 구조 수정
비즈니스 클러스터 SeaweedFS 버킷 k8s-loki k8s-loki, k8s-loki-rules, k8s-tempo
비즈니스 클러스터 추가 스크랩 기본 kube-prometheus-stack Istio Envoy / Istio control-plane / Hubble / Cilium / Flux / GPU Operator / Velero / Kiali 등
Alertmanager 웹훅 플랫폼 알림, 스케일 이벤트 + 외부 알림 웹훅(send_resolved: false)
매니지먼트 클러스터 Ingress enabled: true 주석 처리(비활성)
매니지먼트 클러스터 values Grafana PVC 10Gi, Compactor 15Gi 명시 size 항목 제거, kubeApiServer scrape 30s/29s 추가
비즈니스 클러스터 대시보드 JSON 없음 플랫폼 대시보드 7종(한글). 화면은 매니지먼트 클러스터 Grafana에서 본다

더 이른 구성과의 비교로 적힌 MinIO → SeaweedFS, Promtail → Alloy는 이미 메트릭·로그 구성에 반영되어 있다. 트레이싱 확장 구성의 초기 기록은 2025년이다.

삭제 헬퍼의 실제 동작은 helm uninstall prometheus-stack -n monitoring --wait --timeout 20m이다. 릴리스가 없으면 오류와 helm list를 보여 주고 끝낸다. 네임스페이스, PVC, CRD는 삭제하지 않는다. 잔여 조회 예시는 kubectl get pvc -n monitoring과 CRD 검색이다. 트레이싱 확장 구성은 monitoring.coreos.com 외에 opentelemetry.io, cert-manager.io도 본다. 잔여물을 지울지 말지는 데이터 보존 정책에 따르고, 완전한 정리 절차는 차트 문서에 없다.

검증

매니지먼트 클러스터는 SeaweedFS, Prometheus / Operator, Thanos Query / Store Gateway가 Running이고 bucket-hook Job이 Completed인지 본다. 비즈니스 클러스터는 Prometheus / Alertmanager / Alloy / Loki와 Loki Gateway 노출을 보고, 트레이싱 확장 구성은 Tempo와 OTel Operator / Collector, cert-manager도 본다.

kubectl get pods,svc -n monitoring
# 매니지먼트 클러스터
kubectl get svc -n monitoring | grep -E 'seaweed|thanos|prometheus'
# 비즈니스 클러스터
kubectl get svc -n monitoring | grep -E 'loki|alloy|thanos|prometheus'

s3cmd ls --access_key=<CHANGE_ME> --secret_key=<CHANGE_ME> \
  --host=<MANAGEMENT-VIP>:30333 --host-bucket='<MANAGEMENT-VIP>:30333/%(bucket)s' \
  --no-ssl --signature-v2
s3cmd ls s3://thanos/ --recursive | tail -20

curl -sS "http://<BUSINESS-NodeIP>:<Loki-Gateway-NodePort>/loki/api/v1/labels"
kubectl top nodes
kubectl top pods -n monitoring

Thanos Query Store UI에 Sidecar(business1, management)가 보여야 한다. 메트릭이 S3에 처음 저장되기까지 약 2시간이 걸릴 수 있다. Grafana에서는 데이터소스 thanos와 cluster 변수로 매니지먼트·비즈니스 클러스터가 모두 조회되는지를 확인한다. 트레이싱 확장 구성에서는 Tempo 데이터소스 URL을 http://<tempo-query-frontend-host>:3100으로 맞추고 Additional settings에서 Test한 다음, 트레이스와 서비스 그래프가 보이는지 확인한다.

문제 해결

아래 항목은 트레이싱 확장 구성 가이드에 정리되어 있고, kube-prometheus-stack 66.4.0, node-exporter v1.8.2, Grafana 대시보드처럼 공통 구성 요소와 관련된다. 메트릭·로그 구성 전용 문제 해결 문서는 없고, 같은 증상이 메트릭·로그 구성에서 재현되는지는 확인이 필요하다.

Kubernetes 1.33+에서 v1 Endpoints is deprecated 경고. 배포와 동작은 대체로 정상이다. 당장은 무시할 수 있고, 중장기적으로는 kube-prometheus-stack을 상위 버전으로 올린다.

Pod Security Admission baseline과 node-exporter hostPath. node-exporter가 /proc, /sys, /를 hostPath로 마운트해 baseline 정책(v1.34) 위반 경고가 날 수 있다. warn 모드면 경고만 있고 Pod는 기동한다. 경고를 줄이거나 enforce를 피하려면 monitoring 네임스페이스 라벨을 privileged로 맞추는 방법이 문서에 있다. 정책을 넓히기 전에 클러스터 보안 요구를 먼저 본다.

kubectl label namespace monitoring \
  pod-security.kubernetes.io/warn=privileged \
  pod-security.kubernetes.io/audit=privileged \
  pod-security.kubernetes.io/enforce=privileged \
  --overwrite

Grafana Last 5 minutes만 No data. 한 시간 이상 구간과 Prometheus 메트릭은 있는데 단기만 비면, 노드 NTP가 어긋나 조회 구간과 메트릭 timestamp가 안 맞는 경우가 많다. 흔한 설정은 chrony local stratum 10에 외부 pool을 주석 처리한 구성이다. timedatectl과 chronyc tracking으로 동기화를 확인하고 전 노드를 맞춘다. 더 긴 NTP 절차 문서는 이 차트 설명에 포함되어 있지 않다.

데이터소스는 있는데 패널이 비는 경우. NTP가 정상이어도 데이터소스 prometheus(직접 조회)를 고르면, 대시보드 기본 cluster=management 또는 cluster="$cluster" 필터 때문에 No data가 날 수 있다. 그 데이터에는 cluster 라벨이 없다. prometheus를 쓸 때는 cluster를 비우고, thanos를 쓸 때는 cluster를 고른다. Service 대시보드는 namespace를 선택하지 않으면 전 패널이 비는다. URL 예시는 var-datasource=<DATASOURCE_UID>&var-cluster=이다.
