검증 조건

환경
사내 Kubernetes PaaS, Istio 서비스 메시(Ingress Gateway + Envoy 사이드카)
핵심 결론
istiod는 트래픽 경로 위에 있지 않고 설정(xDS)과 인증서만 내려준다. 그래서 바로 통신이 끊기지는 않지만, 새로 생길 때 문제가 드러난다.

사내 Kubernetes PaaS는 서비스 메시로 Istio를 쓴다. 외부 요청은 모두 Istio Ingress Gateway로 들어오고, 메시 안의 워크로드에는 Envoy 사이드카가 붙어 있다. istiod가 내려가면 무슨 일이 생기는지 보기 전에, 먼저 트래픽이 어떻게 흐르고 istiod가 그 사이에서 무엇을 맡는지 정리해 둔다.

외부 요청 경로

  1. Client → Ingress Gateway: 외부 요청은 istio-system의 Ingress Gateway Pod(Envoy)로 들어온다.
  2. Gateway → SVC: Gateway 리소스가 받을 호스트와 포트를 정하고, VirtualService가 경로를 보고 목적지 Service를 고른다. 메시 안 구간은 Envoy끼리 mTLS로 통신한다.
  3. SVC → Envoy 사이드카: istio-injection=enabled 네임스페이스의 Pod에는 사이드카가 자동 주입되어 있어서, 트래픽은 먼저 사이드카가 받는다.
  4. Envoy → 앱 컨테이너: 사이드카가 같은 Pod 안의 앱(여기서는 Keycloak)으로 넘긴다.

점선은 트래픽이 아니라 설정이다. Gateway·VirtualService·DestinationRule 같은 리소스는 istiod가 Envoy 설정(xDS)으로 바꿔 Ingress Gateway와 모든 사이드카에 내려준다.

Gateway와 VirtualService

실제 구성은 Gateway 하나가 메인 도메인의 80 포트를 받고, VirtualService가 경로별로 서비스를 나눈다. 예를 들어 /auth는 Keycloak으로 보낸다. 도메인과 이름은 예시로 바꿨다.

apiVersion: networking.istio.io/v1beta1
kind: Gateway
metadata:
  name: main-gateway
  namespace: istio-system
spec:
  selector:
    istio: gateway          # 이 라벨이 붙은 Ingress Gateway Pod가 받는다
  servers:
    - hosts:
        - console.example.com
      port:
        name: http2
        number: 80
        protocol: HTTP
apiVersion: networking.istio.io/v1beta1
kind: VirtualService
metadata:
  name: keycloak
  namespace: auth
spec:
  gateways:
    - istio-system/main-gateway
  hosts:
    - console.example.com
  http:
    - match:
        - uri:
            prefix: /auth
      route:
        - destination:
            host: keycloak.auth.svc.cluster.local
            port:
              number: 8080
리소스 맡는 일
Gateway selector로 어떤 Ingress Gateway Pod가 받을지, 어떤 호스트·포트를 열지
VirtualService 들어온 요청을 경로(/auth 등)로 나눠 목적지 Service로 라우팅
DestinationRule 목적지에 도착한 뒤의 정책(로드밸런싱, 서브셋, TLS 모드)

같은 Gateway에 경로 규칙을 붙여 Grafana 같은 다른 서비스도 한 도메인 아래로 모았다. 그 구성은 Grafana 링크 일원화에 따로 정리했다.

컨트롤 플레인과 데이터 플레인

Istio는 두 층으로 나뉜다.

  • 컨트롤 플레인은 설정과 인증서를 배포한다. 1.5부터는 Pilot, Citadel, Galley가 istiod 바이너리 하나로 합쳐졌다.
  • 데이터 플레인은 실제 트래픽을 처리한다. Ingress Gateway, 각 Pod의 Envoy 사이드카, 바깥으로 나가는 Egress Gateway가 여기에 속한다.
구성 요소 역할
Pilot Service Discovery, 트래픽 관리(라우팅, retry, timeout, circuit breaker)
Citadel 인증, mTLS, 키와 인증서 관리
Galley 사용자가 작성한 Istio 설정 검증
Mixer 정책 검사, 텔레메트리 수집. 1.5에서 폐기, 1.8에서 제거

메시 밖으로 나가는 트래픽은 ServiceEntry로 외부 목적지를 등록하고 Egress Gateway를 거쳐 나간다.

istiod 안쪽: Pilot과 Citadel

Pilot: Service Discovery와 트래픽 규칙

  1. 새 인스턴스가 생기면 Platform Adapter가 알림을 받는다.
  2. Platform Adapter는 플랫폼(Kubernetes)의 정보를 Istio 내부의 Abstract Model로 바꾼다.
  3. Envoy API(xDS)가 바뀐 엔드포인트와 트래픽 규칙을 모든 Envoy에 내려준다.

각 Envoy는 Pilot에게 받은 다른 인스턴스 정보로 로드밸런싱을 한다. VirtualService, DestinationRule, AuthorizationPolicy, Sidecar 같은 리소스가 생성·수정·삭제될 때마다 그걸 Envoy 문법으로 컴파일해서 각 Envoy에 업데이트하는 것도 istiod의 일이다.

Citadel: mTLS 인증서

메시 안 마이크로서비스 사이 통신을 mTLS로 암호화하려면 Envoy마다 고유한 인증서가 있어야 한다.

  1. Pod 안의 pilot-agent가 키를 만들고 istiod CA에 CSR을 보낸다.
  2. istiod가 서명한 인증서를 돌려준다.
  3. pilot-agent가 UDS 소켓 위의 SDS로 Envoy에 인증서를 넘긴다.

인증서 발급 흐름은 Tetrate 블로그의 설명을 참고했다.

응용 1: nginx Ingress를 Istio가 처리하게 바꾸기

위 경로는 Gateway와 VirtualService를 쓰는 방식이다. 같은 Ingress Gateway를 쿠버네티스 Ingress(ingressClassName: istio) 만으로 쓰는 방법도 있다. 이 방식에서는 istiod가 Ingress를 읽어 Envoy 라우트를 자동으로 만들기 때문에 Gateway와 VirtualService가 필요 없다. 기존 nginx Ingress로 노출하던 Prometheus, Alertmanager, Kiali를 이 방식으로 옮겼다(Istio 1.22.3).

필요한 리소스는 네 가지다.
리소스 역할
IngressClass controller: istio.io/ingress-controller 지정
meshConfig istiod의 ingress controller 설정
Ingress Host, TLS, 백엔드 Service 정의
TLS Secret HTTPS 종료용. gateway가 있는 istio-system에 있어야 한다
### IngressClass와 meshConfig 
apiVersion: networking.k8s.io/v1
kind: IngressClass
metadata:
  name: istio
spec:
  controller: istio.io/ingress-controller

istiod가 Ingress를 처리하려면 istio-system/istio ConfigMap의 mesh에 ingress controller 설정이 있어야 한다. gateway의 실제 Service 이름과 Pod 라벨에 맞춘다.

defaultConfig:
  discoveryAddress: istiod.istio-system.svc:15012
ingressClass: istio
ingressService: istio-gateway        # 실제 gateway Service 이름
ingressSelector: gateway             # gateway Pod 라벨(istio: gateway)
ingressControllerMode: STRICT        # 지정한 ingressClass만 처리

영향 범위

istiod Deployment가 롤링 재시작된다. 재시작하는 동안에는 설정(xDS) 갱신과 새 Pod 주입이 잠시 늦어질 수 있다.

kubectl get cm istio -n istio-system -o jsonpath='{.data.mesh}'
kubectl rollout restart deploy/istiod -n istio-system
kubectl rollout status deploy/istiod -n istio-system

반영됐는지는 gateway Envoy의 config_dump에 Host 도메인이 들어왔는지로 확인한다.

POD=$(kubectl get pods -n istio-system -l istio=gateway -o jsonpath='{.items[0].metadata.name}')
kubectl exec -n istio-system $POD -c istio-proxy -- \
  curl -s localhost:15000/config_dump | grep prometheus.example.com

TLS Secret과 Ingress

HTTPS 종료에 쓰는 TLS Secret은 gateway가 있는 istio-system에서 읽으므로 그 네임스페이스에 둔다.

kubectl get secret monitoring-tls -n monitoring -o yaml \
  | sed 's/namespace: monitoring/namespace: istio-system/' \
  | kubectl apply -f -

Ingress는 ingressClassName: istio만 바꾸면 된다. Prometheus 예시다.

apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: prometheus-stack-kube-prom-prometheus
  namespace: monitoring
spec:
  ingressClassName: istio
  tls:
  - hosts:
    - prometheus.example.com
    secretName: monitoring-tls
  rules:
  - host: prometheus.example.com
    http:
      paths:
      - path: /
        pathType: Prefix
        backend:
          service:
            name: prometheus-stack-kube-prom-prometheus
            port:
              number: 9090

Alertmanager(9093)와 Kiali(20001)도 같은 형식이다. 이미 nginx용으로 만든 Ingress는 클래스만 바꾼다. Kiali는 nginx 전용 어노테이션을 먼저 지운다.

영향 범위

해당 Ingress를 처리하는 컨트롤러가 nginx에서 Istio로 바뀐다. 전환 순간부터 그 Host의 트래픽은 istio-gateway가 받는다.

kubectl patch ingress prometheus-stack-kube-prom-prometheus -n monitoring \
  --type=json -p='[{"op":"replace","path":"/spec/ingressClassName","value":"istio"}]'

# Kiali: nginx 어노테이션 제거 후 클래스 변경
kubectl annotate ingress kiali -n istio-system \
  nginx.ingress.kubernetes.io/backend-protocol- \
  nginx.ingress.kubernetes.io/secure-backends-
kubectl patch ingress kiali -n istio-system \
  --type=json -p='[{"op":"replace","path":"/spec/ingressClassName","value":"istio"}]'

kubectl get ingress -A의 CLASS 열이 istio인지 확인한다.

gateway를 hostNetwork로

외부 노출은 NodePort 대신 hostNetwork를 택했다. NodePort는 30440, 32207 같은 비표준 포트라 앞단에서 DNAT를 더 해야 하지만, hostNetwork는 노드의 80/443에 바로 바인딩하므로 표준 포트를 쓰고 DNAT가 단순해진다. gateway를 올리는 노드 5대 모두에 istio/proxyv2:1.22.3과 pause:3.9 이미지를 미리 pull해 두었다.

hostNetwork를 쓰면서 만난 문제는 세 가지였다.

이슈 원인 해결
image: auto pull 실패 hostNetwork에서 sidecar injection이 동작하지 않음 injection된 Pod 스펙을 명시적으로 반영
80/443 Permission denied non-root(1337) + hostNetwork에서 sysctl 불가 runAsUser: 0
Gateway와 VirtualService 충돌 K8s Ingress와 Host가 중복 Gateway/VS는 쓰지 않고 K8s Ingress만 사용

최종 gateway DaemonSet의 핵심은 아래와 같다. 정상 동작하던 injection된 gateway Pod의 container와 volumes 스펙을 DaemonSet에 그대로 복사해서 만들었다.

spec:
  template:
    metadata:
      annotations:
        sidecar.istio.io/inject: "false"   # injection 대신 명시적 스펙 사용
    spec:
      hostNetwork: true
      dnsPolicy: ClusterFirstWithHostNet
      containers:
      - name: istio-proxy
        image: <REGISTRY>/istio/proxyv2:1.22.3
        args:
        - proxy
        - router
        - --domain
        - $(POD_NAMESPACE).svc.cluster.local
        securityContext:
          runAsUser: 0
          runAsNonRoot: false
          capabilities:
            add: [NET_BIND_SERVICE]
            drop: [ALL]

Pod IP가 노드 IP로 나오는지, 노드에서 80/443을 Envoy가 LISTEN하는지 확인하면 gateway 쪽 준비는 끝이다.

kubectl get pods -n istio-system -l istio=gateway -o wide
ss -tlnp | grep -E ":80 |:443 "

응용 2: 메트릭 경로와 Kiali Flow가 비는 문제

Kiali의 Graph(Flow)는 Envoy → Prometheus → Kiali 순서로 흘러온 메트릭으로 그려진다. 어느 한 구간이 끊기면 Kiali에는 No data available만 남는다. 이번에는 Prometheus에서 istio_requests_total이 Empty query result였고, Envoy의 /stats/prometheus 엔드포인트 자체는 정상이었다. 원인은 15090 포트를 노출하는 Service가 없다는 것이었다.

kubectl get svc -A | grep 15090
# 결과 없음

영향은 이렇게 번진다.

기능 영향
Prometheus 메트릭 수집 불가
Grafana 데이터 없음
Kiali Flow 그래프 미표시

해결은 Envoy 메트릭용 Service와 ServiceMonitor를 만드는 것이었다.

apiVersion: v1
kind: Service
metadata:
  name: istio-envoy-metrics
  namespace: istio-system
  labels:
    app: istio-proxy
spec:
  ports:
  - name: http-envoy-prom
    port: 15090
    targetPort: 15090
  selector:
    app: istio-proxy
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: istio-envoy
  namespace: monitoring
  labels:
    release: prometheus-stack
spec:
  namespaceSelector:
    any: true
  selector:
    matchExpressions:
    - key: istio-prometheus-ignore
      operator: DoesNotExist
  endpoints:
  - targetPort: 15090
    path: /stats/prometheus
    interval: 15s
[Application Pod] → [사이드카 Envoy :15090] → [Service] → [ServiceMonitor] → [Prometheus] → [Kiali]

적용하고 나면 Kiali Graph에 트래픽 흐름이 그려진다.
