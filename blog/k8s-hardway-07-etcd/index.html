잠긴 글입니다. 저장소 주인만 본문을 볼 수 있습니다.

6편에서 마스터에 ca.crt와 etcd-server 인증서를 배포했다. 이 편에서는 마스터 3대에 etcd v3.5.17을 설치하고 클러스터를 만든 뒤, endpoint status로 세 멤버를 확인한다. etcd는 1편에서 컨트롤 플레인의 상태 저장소로 둔 구성 요소이고, 실제 API 서버 연결은 8편에서 다룬다.

쿠버네티스 API 서버는 클러스터 상태를 etcd에 저장한다. 이 랩은 마스터 3대에 etcd를 두어 클러스터링한다. 클라이언트 포트는 2379, 피어(멤버 간) 포트는 2380이고, 1편 방화벽 표와 같다.

etcd 클러스터 생성 (마스터 3대에서 모두 실행)

GitHub 릴리스에서 etcd v3.5.17 리눅스 amd64 아카이브를 받아 /usr/local/bin에 etcd, etcdctl, etcdutl을 둔다. 주석에 다른 미러의 v3.5.6 URL이 있지만, 실제로 받은 파일과 이후 상태 조회 버전은 3.5.17이다.

5편에서 만든 etcd-server.crt·etcd-server.key와 ca.crt를 /etc/ssl/etcd/ssl로 복사하고, 데이터 디렉터리 /var/lib/etcd를 만든다. 5편 인증서 SAN에는 마스터 세 주소(172.31.1.2–172.31.1.4)와 127.0.0.1이 들어 있다.

이어서 이 노드가 광고·리슨에 쓸 INTERNAL_IP와, 호스트 이름에서 가져온 ETCD_NAME을 넣는다. VM마다 인터페이스 이름(ens33, ens34 등)이 다를 수 있으므로, 먼저 사설망 172.31.1.0/24 주소가 붙은 인터페이스를 확인한 뒤 그 이름으로 INTERNAL_IP를 설정하고 실행한다. 이 값은 --initial-cluster에 적힌 그 노드의 사설망 주소와 같아야 한다.

systemd etcd service 등록 (마스터 3대에서 모두 실행)

마스터 3대에 같은 유닛 파일을 등록한다. --name은 ${ETCD_NAME}이고, 2편에서 맞춘 호스트 이름(k8s-hardway-master01 등)이 아래 --initial-cluster의 멤버 이름과 같아야 한다.

클라이언트와 피어 모두 /etc/ssl/etcd/ssl의 etcd-server.crt·etcd-server.key와 ca.crt를 쓰고, --client-cert-auth와 --peer-client-cert-auth로 인증서 검사를 켠다. 피어 URL은 https://${INTERNAL_IP}:2380, 클라이언트 URL은 https://${INTERNAL_IP}:2379와 로컬 https://127.0.0.1:2379다.

--initial-cluster-state new는 처음 클러스터를 만들 때 쓰는 값이고, 토큰은 etcd-cluster-0이다. 멤버 목록은 k8s-hardway-master01=https://172.31.1.2:2380, master02는 172.31.1.3, master03은 172.31.1.4다. 데이터 디렉터리는 /var/lib/etcd이다.

ubuntu@k8s-hardway-master01:~/hardway/certs# cat <<EOF | sudo tee /etc/systemd/system/etcd.service
[Unit]
Description=etcd
Documentation=https://github.com/coreos
 
[Service]
ExecStart=/usr/local/bin/etcd \\
  --name ${ETCD_NAME} --cert-file=/etc/ssl/etcd/ssl/etcd-server.crt --key-file=/etc/ssl/etcd/ssl/etcd-server.key --peer-cert-file=/etc/ssl/etcd/ssl/etcd-server.crt \\
  --peer-key-file=/etc/ssl/etcd/ssl/etcd-server.key --trusted-ca-file=/etc/ssl/etcd/ssl/ca.crt --peer-trusted-ca-file=/etc/ssl/etcd/ssl/ca.crt --peer-client-cert-auth \\
  --client-cert-auth --initial-advertise-peer-urls https://${INTERNAL_IP}:2380 --listen-peer-urls https://${INTERNAL_IP}:2380 \\
  --listen-client-urls https://${INTERNAL_IP}:2379,https://127.0.0.1:2379 --advertise-client-urls https://${INTERNAL_IP}:2379 \\
  --initial-cluster-token etcd-cluster-0 --initial-cluster-state new --data-dir=/var/lib/etcd \\
 --initial-cluster k8s-hardway-master01=https://172.31.1.2:2380,k8s-hardway-master02=https://172.31.1.3:2380,k8s-hardway-master03=https://172.31.1.4:2380
Restart=on-failure
RestartSec=5
 
[Install]
WantedBy=multi-user.target
EOF

etcd 권한 700확인 (마스터 3대에서 모두 실행)

/var/lib/etcd는 클러스터 상태를 저장하는 디렉터리라서 다른 사용자가 읽지 못하게 700으로 둔다. 아래 첫 조회에서는 drwxr-xr-x이고, chmod 700 뒤에 drwx------로 바뀐다.

# etcd 권한 700 확인
ubuntu@k8s-hardway-master01:~/hardway/certs# ls -al /var/lib | grep etcd
drwxr-xr-x  2 root      root      4096 Jan  6 10:56 etcd
ubuntu@k8s-hardway-master01:~/hardway/certs# sudo chmod 700 /var/lib/etcd
ubuntu@k8s-hardway-master01:~/hardway/certs# ls -al /var/lib | grep etcd
drwx------  2 root      root      4096 Jan  6 10:56 etcd

etcd service 시작 (마스터 3대에서 모두 실행)

daemon-reload 뒤에 etcd를 enable하고 start한다. 출력에 multi-user.target 심볼릭 링크가 만들어졌으므로, 부팅 후에도 기동되도록 등록된 것이다. 마스터 세 대에서는 master01부터 차례로 시작했다.

# etcd service 시작
ubuntu@k8s-hardway-master01:~/hardway/certs# {
   sudo systemctl daemon-reload
   sudo systemctl enable etcd
   sudo systemctl start etcd
}
Created symlink /etc/systemd/system/multi-user.target.wants/etcd.service → /etc/systemd/system/etcd.service.

위 스크린샷에서 etcd.service 상태를 본다.

etcd cluster health check (마스터 3대에서 모두 실행)

ETCDCTL_API=3과 /etc/ssl/etcd/ssl의 서버 인증서로 etcdctl을 쓴다. endpoint status --cluster로 세 멤버를 한 번에 조회한다.

ubuntu@k8s-hardway-master01:~/hardway/certs# export ETCDCTL_API=3
ubuntu@k8s-hardway-master01:~/hardway/certs# export ETCDCTL_CERT=/etc/ssl/etcd/ssl/etcd-server.crt
ubuntu@k8s-hardway-master01:~/hardway/certs# export ETCDCTL_KEY=/etc/ssl/etcd/ssl/etcd-server.key
ubuntu@k8s-hardway-master01:~/hardway/certs# export ETCDCTL_CACERT=/etc/ssl/etcd/ssl/ca.crt

root@k8s-hardway-master01:/var/lib/etcd# etcdctl endpoint status --cluster --write-out=table
+-------------------------+------------------+---------+---------+-----------+------------+-----------+------------+--------------------+--------+
|        ENDPOINT         |        ID        | VERSION | DB SIZE | IS LEADER | IS LEARNER | RAFT TERM | RAFT INDEX | RAFT APPLIED INDEX | ERRORS |
+-------------------------+------------------+---------+---------+-----------+------------+-----------+------------+--------------------+--------+
| https://172.31.1.2:2379 | 101495a310ac1a7b |  3.5.17 |   20 kB |      true |      false |         2 |          9 |                  9 |        |
| https://172.31.1.4:2379 | 304466080bac6f25 |  3.5.17 |   20 kB |     false |      false |         2 |          9 |                  9 |        |
| https://172.31.1.3:2379 | aa636e2a05615395 |  3.5.17 |   20 kB |     false |      false |         2 |          9 |                  9 |        |
+-------------------------+------------------+---------+---------+-----------+------------+-----------+------------+--------------------+--------+

표에서 엔드포인트는 https://172.31.1.2:2379, https://172.31.1.4:2379, https://172.31.1.3:2379이고, 버전은 모두 3.5.17이다. IS LEADER는 172.31.1.2만 true이고 나머지 둘은 false다. IS LEARNER는 모두 false이며, ERRORS 칸은 비어 있다. DB SIZE는 세 노드 모두 20 kB이고, RAFT TERM은 2, RAFT INDEX와 RAFT APPLIED INDEX는 9다. 멤버가 세 대이고 리더가 하나이며 오류가 없으면 이 단계의 성공 기준을 충족한 것이다.

마스터 3곳 출력 결과

이 단계에서 보면 되는 것은 다음과 같다.

  • 세 마스터에서 etcd 유닛이 등록되고 기동되는지
  • /var/lib/etcd 권한이 700인지
  • endpoint status에 멤버 세 대가 나오고, IS LEADER가 하나만 true이며, ERRORS가 비어 있는지
  • 버전이 모두 3.5.17인지

안 될 때 확인할 곳:

  • --initial-cluster의 멤버 이름과 ${ETCD_NAME}, IP가 각 노드와 맞는지 본다.
  • listen·advertise 주소가 그 노드의 사설 IP인지, 피어 URL에 127.0.0.1을 쓰지 않았는지 본다.
  • /var/lib/etcd 권한과, initial-cluster-state=new로 이미 데이터가 있는 디렉터리에 다시 조인하지 않았는지를 본다.
  • journalctl -u etcd에 TLS나 SAN 오류가 없는지 본다. SAN 목록은 5편에 있다.

여기까지 되면 마스터 3대의 etcd 클러스터가 준비된 것이다. 다음은 8편에서 컨트롤 플레인을 올리고, kube-apiserver가 이 엔드포인트에 연결한다.
