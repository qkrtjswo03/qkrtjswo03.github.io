Grafana Tempo 분산 배포: Trace·Span 개념부터 MinIO 백엔드, HA 구성까지

핵심 결론
Tempo는 객체 스토리지만 있으면 돌아간다. tempo-distributed를 MinIO 백엔드로 배포하고, ingester·distributor·querier·query-frontend는 복수로, compactor는 하나로 운영한다.

로그는 Loki, 메트릭은 Prometheus로 모으고 있었는데 트레이스가 빠져 있었다. 이 시리즈는 OpenTelemetry로 트레이스를 모아 Grafana Tempo에 저장하고 Grafana에서 보기까지의 과정이다. 첫 글은 Tempo 자체, 즉 개념과 구성 요소, 분산 배포다.

Trace와 Span

Trace는 분산된 마이크로서비스 시스템에서 요청(트랜잭션) 하나가 여러 서비스와 구성 요소를 거쳐 처리되는 전체 경로를 기록한 것이다.

구성 요소 설명
Trace ID 요청이 시작될 때 만들어지는 고유 식별자. 요청 전체에 공통으로 적용된다
Span Trace를 이루는 기본 단위. 작업이나 이벤트 하나를 뜻하며 시작·종료 시간, 태그, 로그를 담는다

Trace 하나는 여러 Span으로 이루어지고, Span은 계층적으로 이어져 요청의 흐름을 표현한다.

Tempo

Tempo는 Grafana가 만든 트레이스 백엔드이고 Grafana가 프런트엔드 역할을 한다. Jaeger, Zipkin, OpenTelemetry 같은 일반적인 오픈소스 트레이싱 프로토콜을 받을 수 있고, 동작에 필요한 것은 객체 스토리지뿐이다. Grafana, Prometheus, Loki와 통합되어 있다. 이번에는 MinIO를 S3 백엔드로 썼다.

아키텍처는 Loki와 매우 비슷하다.

컴포넌트 역할
distributor 다양한 형식(Jaeger, Zipkin, OpenTelemetry)의 트레이스를 수신하고 ingester로 분배
ingester 트레이스를 블록으로 묶어 S3 백엔드에 저장
query-frontend 들어온 쿼리의 검색 공간을 나눠 querier에 분산
querier ingester나 백엔드 저장소에서 요청한 Trace ID를 찾음
compactor 백엔드의 트레이스 블록을 압축
metrics-generator(선택) 수집된 트레이스에서 RPS, 오류율 같은 기본 메트릭을 생성
memcached(선택) 컴포넌트들이 쓰는 캐시. Parquet bloom filter, footer 등을 캐시

모든 컴포넌트는 하나의 바이너리에 들어 있고 배포 모드가 두 가지다. 모놀리식 모드는 모든 컴포넌트를 한 프로세스(컨테이너)에서 돌린다. 마이크로서비스 모드는 컴포넌트를 별도 프로세스로 배포하고, 확장성과 HA는 여기서 정해진다. 이번에는 MinIO를 백엔드로 둔 마이크로서비스 모드로 설치했다.

수집   distributor → ingester → MinIO에 업로드
최적화 compactor (Parquet 정리, 병합)
조회   query-frontend → querier → MinIO에서 읽기
부가   metrics-generator (trace → metrics), memcached (Parquet 메타데이터 캐시)

배포

Helm 저장소를 추가하고 네임스페이스를 만든 뒤 차트를 받는다.

helm repo add grafana https://grafana.github.io/helm-charts
helm repo update
kubectl create namespace tempo
helm pull grafana/tempo-distributed --version 1.32.2 --untar

핵심은 OTLP 수신 활성화, S3(MinIO) 백엔드, 그리고 게이트웨이 노출이다.

# tempo-values.yaml
traces:
  otlp:
    http:
      enabled: true
      receiverConfig: {}
    grpc:
      enabled: true
      receiverConfig: {}
metricsGenerator:
  enabled: true
  config:
    storage:
      remote_write:
        - url: http://prometheus-stack-prometheus.monitoring:9090/api/v1/write
          send_exemplars: false
global_overrides:
  metrics_generator_processors:
    - service-graphs
  per_tenant_override_config: /runtime-config/overrides.yaml
storage:
  trace:
    backend: s3
    s3:
      bucket: k8s-tempo
      endpoint: minio.minio.svc.cluster.local:9000
      region: null
      access_key: <CHANGE_ME>
      secret_key: <CHANGE_ME>
      insecure: true
distributor:
  config:
    log_received_spans:
      enabled: true
server:
  http_listen_port: 3100
  grpc_listen_port: 9095
  ring:
    kvstore:
      store: memberlist
gateway:
  enabled: true
  replicas: 1
  service:
    port: 80
    type: NodePort
    clusterIP: null
    nodePort: 31538
helm upgrade tempo grafana/tempo-distributed --version 1.32.2 -f tempo-values.yaml -n tempo

metricsGenerator와 service-graphs 설정은 Service Graph 글에서 쓴다. 차트의 Tempo 버전은 2.7.1이었다. k8s-tempo 버킷은 MinIO 차트 values의 buckets로 만들었고, Tempo 전용 사용자와 정책에 s3:GetObject, s3:PutObject, s3:DeleteObject, s3:ListBucket, s3:GetObjectTagging, s3:PutObjectTagging 권한을 줬다.

HA가 필요한 컴포넌트

컴포넌트 HA 필요 이유
ingester 반드시 복수 쓰기 경로의 중심
distributor 필요 모든 트래픽이 지나므로 복수 배포 후 Service로 로드밸런싱
querier 필요 조회 요청을 여러 querier에 분산
query-frontend 필요 쿼리 병목을 막고, Grafana 쿼리를 받으므로 복수 구성 권장
compactor 보통 하나 병렬로 돌리면 데이터 충돌 위험이 있어 일반적으로 하나만 실행
metrics-generator 선택 필요할 때만 HA 구성. HA보다는 필요에 따라 스케일링
memcached 선택 캐시라서 replica를 늘릴 수 있지만 critical path는 아님

Grafana 데이터 소스

Grafana에서 Tempo를 연결할 때 URL은 같은 클러스터 안이면 http://tempo-query-frontend-discovery.tempo:3100, 다른 클러스터의 Grafana에서는 게이트웨이를 연 NodePort를 쓴다. 이번 구성에서 매니지먼트 클러스터의 Grafana는 비즈니스 클러스터의 Tempo를 <BASTION_IP>:31538로 붙였다.
