검증 조건

테스트 버전
  • Istio 1.25.2
  • kindest/node v1.30.2
  • Gateway API CRD v1.2.1
환경
Ubuntu VM의 Docker + kind(컨트롤 플레인 1, 워커 2)
검증 시점
2025-04
핵심 결론
ambient 프로파일을 설치한 뒤 네임스페이스에 istio.io/dataplane-mode=ambient 라벨을 붙이면 Pod 재시작 없이 mTLS가 적용되고, istioctl ztunnel-config에서 HBONE으로 보인다.

개요에서 본 구성 요소를 직접 확인하려고 kind 위에 Ambient를 올려 봤다. 클러스터를 만들고 Istio를 설치하고, Bookinfo를 메시에 넣고 Gateway API로 외부에 열고 Kiali로 보는 것까지의 실습이다.

1. kind 클러스터

Ubuntu 가상 머신에 Docker와 kind를 설치한 뒤 컨트롤 플레인 1대와 워커 2대로 클러스터를 만든다.

# kind-cluster-config.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: ambient
nodes:
- role: control-plane
  image: kindest/node:v1.30.2
- role: worker
  image: kindest/node:v1.30.2
- role: worker
  image: kindest/node:v1.30.2
kind create cluster --config kind-cluster-config.yaml

2. istioctl 설치

시스템 아키텍처(uname -m의 x86_64 또는 arm64)에 맞게 공식 스크립트로 받는다. 이번에는 1.25.2를 썼다.

curl -L https://istio.io/downloadIstio | sh -
cd istio-1.25.2
sudo cp bin/istioctl /usr/local/bin/
istioctl version

아직 클러스터에 Istio가 없으므로 client version: 1.25.2와 함께 Istio is not present in the cluster가 나온다.

3. Gateway API CRD

트래픽 라우팅에 Kubernetes Gateway API를 쓸 것이다. 대부분의 클러스터에는 CRD가 기본으로 없으므로 먼저 설치한다.

kubectl get crd gateways.gateway.networking.k8s.io &> /dev/null || \
kubectl apply -f https://github.com/kubernetes-sigs/gateway-api/releases/download/v1.2.1/standard-install.yaml

gatewayclasses, gateways, grpcroutes, httproutes, referencegrants CRD가 생긴다.

4. Ambient 설치

ambient 프로파일로 설치한다. 이번에는 전통적인 Istio Gateway도 쓰려고 Ingress Gateway 컴포넌트를 켰다. Ambient에서도 Ingress Gateway, VirtualService, DestinationRule은 그대로 쓸 수 있다.

istioctl install \
  --set profile=ambient \
  --set "components.ingressGateways[0].enabled=true" \
  --set "components.ingressGateways[0].name=istio-ingressgateway" \
  --skip-confirmation

끝나면 Istio core, Istiod, CNI, Ztunnel이 설치되었다는 메시지가 나온다.

kubectl get all -n istio-system
  • istio-cni-node와 ztunnel은 DaemonSet이라 노드 수(3)만큼 Pod가 뜬다.
  • istiod는 Deployment이고, CPU 사용량으로 개수를 조정하는 HPA도 함께 구성된다.

ztunnel 로그 읽기

ztunnel 로그에서 inpod로 걸러 보면 Ambient가 Pod 안에서 어떻게 동작하는지 단서가 나온다.

kubectl logs ds/ztunnel | grep inpod
키워드 의미
inpodEnabled: true in-pod Ambient 모드가 켜져 있다
inpodUds: /var/run/ztunnel/ztunnel.sock ztunnel과 workload가 Unix Domain Socket으로 통신한다
handling new stream 새 workload 연결 스트림을 받았다
pod received snapshot sent workload 상태 스냅샷을 받았다
pod delete request, draining proxy workload가 종료되어 프록시 연결을 정리하는 중이다

5. 메시에 Bookinfo 넣기

Bookinfo는 Istio 기능을 시연하는 데 쓰는 샘플로, 마이크로서비스 네 개로 구성된다.

kubectl apply -f https://raw.githubusercontent.com/istio/istio/release-1.25/samples/bookinfo/platform/kube/bookinfo.yaml
kubectl apply -f https://raw.githubusercontent.com/istio/istio/release-1.25/samples/bookinfo/platform/kube/bookinfo-versions.yaml

처음에는 메시 밖이다. 데모 애플리케이션의 트래픽은 ztunnel을 거치지 않고 Kubernetes Service 방식으로 통신하며, Pod 간 트래픽도 mTLS로 보호되지 않는다. 여기서 네임스페이스에 라벨 하나만 붙이면 편입된다.

kubectl label namespace default istio.io/dataplane-mode=ambient
kubectl get ns default --show-labels

애플리케이션을 다시 시작하거나 배포하지 않아도 모든 Pod 사이에 mTLS가 적용된다. 편입 상태는 istioctl로 확인한다. PROTOCOL이 HBONE으로 나오는 Pod가 메시에 들어온 것이다.

istioctl ztunnel-config workload | grep HBONE
default   details-v1-xxxxxxxxxx-xxxxx       <NODE_IP>  ambient-worker2   None   HBONE
default   productpage-v1-xxxxxxxxxx-xxxxx   <NODE_IP>  ambient-worker2   None   HBONE
default   ratings-v1-xxxxxxxxxx-xxxxx       <NODE_IP>  ambient-worker2   None   HBONE
default   reviews-v1-xxxxxxxxxx-xxxxx       <NODE_IP>  ambient-worker2   None   HBONE

6. Gateway API로 노출

Gateway API 리소스로 bookinfo-gateway와 HTTPRoute를 만든다.

kubectl apply -f https://raw.githubusercontent.com/istio/istio/release-1.25/samples/bookinfo/gateway-api/bookinfo-gateway.yaml

Istio는 이 Gateway를 처리할 Pod(bookinfo-gateway-istio)를 자동으로 만들고, 기본으로 LoadBalancer 서비스를 만든다. 이번에는 port-forward로 접근할 것이므로 서비스 유형을 ClusterIP로 바꾸는 어노테이션을 붙였다.

kubectl annotate gateway bookinfo-gateway networking.istio.io/service-type=ClusterIP --namespace=default
kubectl get gateway

PROGRAMMED가 True가 되면 준비된 것이다. 포트 포워딩으로 연다.

kubectl port-forward svc/bookinfo-gateway-istio 8080:80

브라우저에서 http://localhost:8080/productpage를 열면 Bookinfo가 보이고, 새로 고칠 때마다 reviews 서비스의 버전이 바뀌며 별점 표시가 달라진다.

kubectl get gw와 kubectl get gateway

둘은 다른 리소스를 본다. 헷갈리기 쉬워서 정리해 둔다.

명령 보는 리소스
kubectl get gw Istio Gateway(networking.istio.io) 커스텀 리소스. 전통적인 Istio Gateway
kubectl get gateway Kubernetes Gateway API(gateway.networking.k8s.io) 표준 리소스

7. 시각화: Kiali

Prometheus와 Kiali 애드온을 올리고 대시보드를 연다.

kubectl apply -f https://raw.githubusercontent.com/istio/istio/release-1.25/samples/addons/prometheus.yaml
kubectl apply -f https://raw.githubusercontent.com/istio/istio/release-1.25/samples/addons/kiali.yaml
istioctl dashboard kiali

Traffic Graph에서 default 네임스페이스를 고르면 Bookinfo의 호출 관계가 그려진다.

8. 요청 흐름 비교

Sidecar와 Ambient는 요청이 지나가는 길이 다르다.

Sidecar:  Client → Ingress Gateway(Envoy) → VirtualService → DestinationRule
                 → Service → Pod[App + istio-proxy(Envoy)]

Ambient:  Client → Ingress Gateway → VirtualService + DestinationRule
                 → ztunnel(노드별 L4 프록시) → (필요하면 waypoint proxy로 L7 정책)
                 → Destination Pod

참고로 사이드카 모드로 돌던 사내 서비스 Pod 15개의 istio-proxy 컨테이너를 kubectl top pods --containers로 보면 메모리가 대략 5967Mi, CPU가 27m씩이었다. Pod마다 이만큼이 따로 붙는 셈이고, 편차는 트래픽량, 연결 수, 라우팅 구성 크기, telemetry와 로그 설정, Sidecar 이미지 버전 차이에서 온다.

  • Istio
  • Ambient Mesh
  • ztunnel
  • kind
  • Kiali
