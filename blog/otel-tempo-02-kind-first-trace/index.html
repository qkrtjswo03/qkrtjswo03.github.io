검증 조건

테스트 버전
  • kind node v1.29.7
  • tempo-distributed chart 1.33.0 (Tempo 2.7.1)
  • cert-manager v1.16.1
  • otelcol-contrib 0.123.0
환경
kind (control-plane 1 + worker 2)
검증 시점
2025-04
핵심 결론
Collector의 OTLP 수신 → Tempo 전송 파이프라인과 Instrumentation 리소스, Pod 어노테이션 한 줄이면 앱 코드를 고치지 않고 Trace가 Tempo에 쌓인다.

운영 환경에 바로 붙이기 전에 kind로 가장 작은 트레이스 파이프라인을 만들어 봤다. 목표는 Kubernetes에서 앱 코드를 수정하지 않고 OpenTelemetry 구성만으로 트레이스를 자동 수집하는 것이다.

흐름은 `앱 → OpenTelemetry Collector → Tempo → Grafana`다. 순서는 다음과 같다.
  1. kind 클러스터 생성
  2. Grafana 설치
  3. Tempo 설치
  4. OpenTelemetry Operator, Collector, Instrumentation 리소스 구성
  5. 어노테이션을 단 샘플 앱 배포
  6. Grafana에 Tempo 데이터 소스를 추가하고 조회

1. kind 클러스터

컨트롤 플레인 1대, 워커 2대로 만들었다.

# otel-cluster-config.yaml
kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: oteltest
nodes:
- role: control-plane
  image: kindest/node:v1.29.7
  extraPortMappings:
  - containerPort: 80
    hostPort: 80
    protocol: TCP
  - containerPort: 443
    hostPort: 443
    protocol: TCP
- role: worker
  image: kindest/node:v1.29.7
- role: worker
  image: kindest/node:v1.29.7
kind create cluster --config otel-cluster-config.yaml
kubectl get nodes

3. Tempo

Tempo는 Grafana와 같은 Helm 저장소를 쓴다. 차트 이름은 grafana/tempo가 아니라 **grafana/tempo-distributed**여야 한다. 이 실습에서는 OTLP 수신과 service-graphs만 켠 최소 values를 썼다. (S3 백엔드까지 붙이는 배포는 앞 글)

# tempo-values.yaml
traces:
  otlp:
    http:
      enabled: true
      receiverConfig: {}
    grpc:
      enabled: true
      receiverConfig: {}
global_overrides:
  metrics_generator_processors:
  - service-graphs
kubectl create namespace tempo
helm install -n tempo tempo grafana/tempo-distributed -f tempo-values.yaml
kubectl get pods,svc -n tempo

차트 1.33.0, Tempo 2.7.1이 설치됐고 compactor, distributor, ingester 3개, memcached, querier, query-frontend가 Running이 됐다. distributor Service는 OTLP 포트 4317, 4318을 연다.

4. Operator와 Collector

Collector는 Helm으로도 설치할 수 있지만 이번에는 OpenTelemetry Operator로 설치했다. Operator는 cert-manager가 먼저 있어야 한다.

kubectl apply -f https://github.com/cert-manager/cert-manager/releases/download/v1.16.1/cert-manager.yaml
kubectl apply -f https://github.com/open-telemetry/opentelemetry-operator/releases/latest/download/opentelemetry-operator.yaml

Operator가 올라오면 OpenTelemetryCollector, Instrumentation CRD가 생긴다. 먼저 트레이스만 Tempo로 보내는 최소 Collector를 만들었다.

apiVersion: opentelemetry.io/v1alpha1
kind: OpenTelemetryCollector
metadata:
  name: collector
  namespace: otel-trace
spec:
  config: |
    receivers:
      otlp:
        protocols:
          grpc:
            endpoint: 0.0.0.0:4317
          http:
            endpoint: 0.0.0.0:4318
    processors:
      memory_limiter:
        check_interval: 1s
        limit_percentage: 75
        spike_limit_percentage: 15
      batch:
        send_batch_size: 10000
        timeout: 10s
    exporters:
      otlphttp/tempo:
        endpoint: http://tempo-distributor.tempo.svc.cluster.local:4318
    service:
      pipelines:
        traces:
          receivers: [otlp]
          processors: [memory_limiter, batch]
          exporters: [otlphttp/tempo]
kubectl create ns otel-trace
kubectl apply -f otel.yaml
kubectl get pods,svc -n otel-trace

receivers → processors → exporters가 service.pipelines에서 이어진다. OTLP로 4317(gRPC), 4318(HTTP)을 받아 메모리 제한과 배치를 거친 뒤 Tempo distributor로 보낸다. Operator는 collector-collector Service와 collector-collector-monitoring(8888) 같은 Service를 만들어 준다. Pod 로그에 Everything is ready. Begin running and processing data.가 나오면 준비 끝이다. 이 실습의 Collector 버전은 0.123.0이었다.

5. Auto-Instrumentation

코드에 OpenTelemetry SDK를 직접 넣어 트레이스를 만들 수도 있지만, 그러면 앱마다 코드를 고쳐야 한다. Operator의 Instrumentation 리소스를 쓰면 코드 수정 없이 트레이스(와 설정에 따라 로그)를 수집할 수 있다. 대신 직접 코드에 정의하는 방식보다 세밀한 제어는 어렵다.

Instrumentation은 대상 앱과 같은 네임스페이스에 만든다.

apiVersion: opentelemetry.io/v1alpha1
kind: Instrumentation
metadata:
  name: python-instrumentation
  namespace: app
spec:
  exporter:
    endpoint: http://collector-collector.otel-trace.svc.cluster.local:4317
  propagators:
    - tracecontext
    - baggage
  python:
    env:
      - name: OTEL_PYTHON_LOGGING_AUTO_INSTRUMENTATION_ENABLED
        value: 'true'
필드 의미
spec.exporter 수집한 데이터를 보낼 Collector 주소
spec.propagators Trace ID 컨텍스트를 서비스 사이에 전달하는 방식. 여러 서비스를 호출하는 MSA라면 맞춰야 한다
spec.sampler 추적 비율. parentbased_traceidratio에 argument "1"이면 100% 기록

Java 앱이라면 spec.java.env에 로그백 어펜더(OTEL_INSTRUMENTATION_LOGBACKAPPENDER_ENABLED)와 OTLP 엔드포인트를 주면 되고, 자세한 설정은 Collector와 Operator 글에 정리했다.

6. 샘플 앱 배포

1~6 사이의 주사위 눈을 반환하는 Python Flask 앱(GET /roll)을 만들어 이미지로 빌드했다.

FROM python:3.9-slim
WORKDIR /app
COPY requirements.txt /app/
RUN pip install --no-cache-dir -r requirements.txt
COPY . /app/
CMD ["python", "dice_roll.py"]
docker build -t <REGISTRY>/dice-roller-app .
docker push <REGISTRY>/dice-roller-app

Deployment의 Pod 템플릿에 어노테이션 한 줄만 추가한다. 컨테이너가 여러 개라면 instrumentation.opentelemetry.io/container-names로 대상 컨테이너를 지정한다.

apiVersion: apps/v1
kind: Deployment
metadata:
  labels:
    app: myapp
  name: myapp-deployment
  namespace: app
spec:
  replicas: 1
  selector:
    matchLabels:
      app: myapp
  template:
    metadata:
      annotations:
        instrumentation.opentelemetry.io/inject-python: "true"
      labels:
        app: myapp
    spec:
      containers:
      - image: <REGISTRY>/dice-roller-app
        name: myapp
        ports:
        - containerPort: 80
          protocol: TCP

Operator가 init 컨테이너로 Python 에이전트를 주입해 준다.

7. Grafana에서 확인

Grafana의 Connections → Data sources → Add new data source에서 Tempo를 고르고 URL에 http://tempo-query-frontend-discovery.tempo.svc.cluster.local:3100/를 넣은 뒤 Save & Test로 연결을 확인한다.

트레이스를 만들려면 앱에 요청을 보내야 한다.

kubectl port-forward pod/<POD_NAME> 5000:5000
curl http://localhost:5000/roll
# {"dice_roll":3}

Explore에서 데이터 소스를 Tempo로 두고 Search로 보면 myapp-deployment 서비스의 GET /roll Trace가 요청마다 쌓여 있다.

Trace ID로 열면 Trace 하나의 상세가 보인다. 이번 요청은 `GET /roll` 하나에 6.55ms가 걸렸고 Span은 1개다. 앱이 다른 서비스를 호출하지 않으니 Span이 하나뿐인 건 자연스럽다. ## 정리와 한계

트레이스만으로는 애플리케이션의 성능을 다 볼 수 없다. HTTP 요청이 초당 얼마나 들어오는지, 요청당 응답 시간은 얼마인지는 메트릭이 필요하고, 오류의 원인은 로그가 필요하다. Trace ID를 연결 고리로 세 신호를 함께 보는 것이 목표고, 다음 글에서 Collector 설정을 그쪽으로 넓힌다.
