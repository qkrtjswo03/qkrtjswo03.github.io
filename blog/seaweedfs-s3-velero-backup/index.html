핵심 결론
SeaweedFS S3 게이트웨이(8333)에 IAM 설정을 올린 뒤, Velero Secret과 BackupStorageLocation의 s3Url·bucket만 맞추면 백업 오브젝트가 버킷에 쌓인다.

Velero 백업 저장소를 외부 S3 호환 스토리지에 두고 싶을 때, SeaweedFS 를 단일 바이너리로 올려 S3 게이트웨이를 쓰는 방법이 있다. Ubuntu 24.04에서 SeaweedFS 4.05를 설치하고, s3cmd로 버킷을 만든 다음 Velero에 붙인 과정을 정리한다.

호스트 IP·Access Key·Secret Key는 모두 플레이스홀더다. <NODE_IP>, CHANGE_ME_ACCESS_KEY, CHANGE_ME_SECRET_KEY 자리에 환경 값을 넣는다. 문서·저장소에 실키를 남기지 말 것.

2. SeaweedFS 설치

2.1 패키지

apt update
apt install -y jq curl wget

2.2 바이너리

wget https://github.com/seaweedfs/seaweedfs/releases/download/4.05/linux_amd64.tar.gz
tar -xzf linux_amd64.tar.gz
mv weed /usr/local/bin/
chmod +x /usr/local/bin/weed
weed version

출력 예:

version 30GB 4.05 87b71029f75efc2fe6f1bcf12a3f129127f04e90 linux amd64

2.3 서비스 계정·데이터 디렉터리

sudo useradd -r -s /usr/sbin/nologin seaweed
sudo mkdir -p /data/seaweed
sudo chown -R seaweed:seaweed /data/seaweed
id seaweed
ls -ld /data/seaweed

3. S3 IAM 설정

sudo mkdir -p /etc/seaweedfs
sudo vi /etc/seaweedfs/s3.conf
{
  "identities": [
    {
      "name": "velero",
      "credentials": [
        {
          "accessKey": "CHANGE_ME_ACCESS_KEY",
          "secretKey": "CHANGE_ME_SECRET_KEY"
        }
      ],
      "actions": [
        "Admin",
        "Read",
        "Write",
        "List"
      ]
    }
  ]
}
sudo chown seaweed:seaweed /etc/seaweedfs/s3.conf
sudo chmod 600 /etc/seaweedfs/s3.conf

4. systemd 서비스

sudo vi /etc/systemd/system/seaweedfs.service
[Unit]
Description=SeaweedFS
After=network.target

[Service]
User=seaweed
Group=seaweed
Type=simple
ExecStart=/usr/local/bin/weed server \
  -ip=<NODE_IP> \
  -dir=/data/seaweed \
  -volume.max=1000 \
  -s3 \
  -s3.config=/etc/seaweedfs/s3.conf
Restart=always
RestartSec=5
LimitNOFILE=65535

[Install]
WantedBy=multi-user.target

seaweedfs 유닛이 재시작되며, 그 동안 S3(8333)·Master·Volume 포트 접근이 잠시 끊길 수 있다.

sudo systemctl daemon-reload
sudo systemctl restart seaweedfs
sudo systemctl enable seaweedfs
sudo systemctl status seaweedfs

ss -tulnp | grep weed

5. s3cmd로 버킷 검증

sudo apt update
sudo apt install -y s3cmd
s3cmd --version
s3cmd version 2.4.0

s3cmd --configure에서 Access/Secret Key, Endpoint를 <NODE_IP>:8333으로 맞추고 HTTPS는 끈다. 설정 요약 예:

host_base = <NODE_IP>:8333
host_bucket = <NODE_IP>:8333/%(bucket)
use_https = False

버킷 생성·업로드:

s3cmd mb s3://velero
s3cmd put test.txt s3://velero/
s3cmd ls s3://velero/

디렉터리 상태 JSON에 collection":"velero"가 보이면 오브젝트가 Master 토폴로지에 잡힌 것이다.

curl http://localhost:9333/dir/status

6. Velero 연동

Bastion(또는 배포 호스트)에서 엔드포인트 연결만 먼저 확인한다. AccessDenied XML이면 네트워크는 통과한 것이다.

curl http://<NODE_IP>:8333

기존 BackupStorageLocation·Secret을 백업한 뒤 Secret을 교체한다.

kubectl get backupstoragelocation default -n velero -o yaml > backupstoragelocation-backup.yaml
kubectl get secret velero -n velero -o yaml > velero-secret-backup.yaml

영향 범위

velero 네임스페이스의 velero Secret이 삭제·재생성된다. 그동안 새 백업 생성이 실패할 수 있다.

kubectl delete secret velero -n velero
kubectl create secret generic velero \
  -n velero \
  --from-file=cloud=credentials-velero

Helm로 관리 중이라면 라벨·어노테이션을 맞춘다.

kubectl label secret velero -n velero \
  app.kubernetes.io/instance=velero \
  app.kubernetes.io/managed-by=Helm \
  app.kubernetes.io/name=velero \
  helm.sh/chart=velero-10.0.12

kubectl annotate secret velero -n velero \
  meta.helm.sh/release-name=velero \
  meta.helm.sh/release-namespace=velero

BackupStorageLocation 예시:

spec:
  config:
    region: us-east-1
    s3ForcePathStyle: "true"
    s3Url: http://<NODE_IP>:8333
  objectStorage:

테스트 백업:

velero backup create seaweed-test --include-namespaces default

s3cmd ls s3://velero/

버킷 아래에 backups/·restores/ 디렉터리가 보이면 저장소 연동은 된 것이다. 첫 시도가 PartiallyFailed였다가 설정 수정 후 Completed로 끝난 경우가 있었다.

7. 인증 키 이슈 메모

MinIO 기본 계정 문자열을 SeaweedFS에 그대로 넣었는데, 실제로는 S3 config가 프로세스에 반영되지 않아 등록된 access key가 0개인 상태에서 Thanos storegateway 등이 인증 실패로 CrashLoopBackOff에 빠질 수 있다.

증상 로그 예:

The access key ID you provided does not exist in our records.
InvalidAccessKeyId (V2 signed): attempted key '…' not found.
Available keys: 0, Auth enabled: true

확인할 것:

  • Pod/호스트의 S3 config 파일 내용과 마운트 경로
  • weed 프로세스 인자의 -s3.config=… 경로
  • 클라이언트(s3cmd 등)가 같은 키·엔드포인트·signature 버전을 쓰는지

키가 config에 있는데도 Available keys: 0이면, 파일이 비었거나 심볼릭 링크·마운트가 기대한 내용을 가리키지 않는 경우가 많다. config를 고친 뒤에는 SeaweedFS(또는 해당 Pod)를 한 번 재시작해 프로세스가 설정을 다시 읽게 한다.

7.1 Job에서 키를 넣을 때는 curl 대신 weed shell

all-in-one으로 Kubernetes에 올렸을 때도 같은 증상을 만났다. 초기화용 Job에서 S3 사용자와 키를 넣으려 했는데 SeaweedFS 로그에는 attempted key '…' not found. Available keys: 1, Auth enabled: true가 계속 찍혔다. SeaweedFS Pod 안에서 weed shell로 넣는 것은 잘 됐고, Job에서 curl로 S3 게이트웨이의 관리 API(PUT :8333/admin/s3/user)를 호출하는 방식만 실패했다.

구분 weed shell + s3.configure curl → :8333/admin/...
경로 마스터(클러스터 설정) 쪽 셸 프로토콜 S3 게이트웨이 HTTP 관리 API
준비 조건 마스터에 연결되는 시점 8333이 열려 있어도 IAM·Filer 같은 백엔드 준비가 끝났다는 뜻은 아님
버전 Job 이미지 태그가 클러스터와 다르면 동작이 달라질 수 있음 REST 경로·바디 형식이 버전별로 다를 수 있음

같은 "S3 사용자 등록"이라도 호출하는 서버와 프로토콜이 달라서 한쪽만 성공할 수 있다. 해결은 세 가지였다.

  1. Job에서는 curl 대신 weed shell의 s3.configure를 쓴다.
  2. 이미지를 클러스터와 같은 태그로 고정한다(docker.io/chrislusf/seaweedfs:4.05). latest는 피한다.
  3. 8333만 기다리지 말고 weed shell -master=...에 맞는 마스터 포트(보통 9333)가 열릴 때까지 기다린다.
apiVersion: batch/v1
kind: Job
metadata:
  name: seaweedfs-init-iam
  namespace: monitoring
spec:
  backoffLimit: 5
  template:
    spec:
      restartPolicy: OnFailure
      containers:
        - name: init
          image: docker.io/chrislusf/seaweedfs:4.05   # 클러스터와 같은 버전으로
          command:
            - sh
            - -c
            - |
              echo "waiting for master..."
              until nc -z seaweedfs-all-in-one.monitoring 9333; do sleep 2; done
              sleep 5
              weed shell -master=seaweedfs-all-in-one.monitoring:9333 <<'EOF'
              s3.configure -user=admin -access_key=<CHANGE_ME> -secret_key=<CHANGE_ME> -actions=Read,Write,List,Tagging,Admin -apply
              EOF

Service 이름, 네임스페이스, 마스터 포트는 실제 배포 값에 맞춘다. 액세스 키와 시크릿은 Secret으로 주입하는 편이 낫다.

8. 여러 노드로 늘리기: Master·Volume·Filer·S3 분리

지금까지는 weed server 하나에 모든 걸 넣은 단일 노드 구성이다. 워커 노드 3대에 같은 바이너리로 Master, Volume, Filer, S3 Gateway를 각각 systemd 서비스로 나눠 올린 구성도 해 봤다. 이 구성은 성능 테스트(warp)를 준비하려고 만든 것이다.

서비스 포트 역할
Master 9333 클러스터 메타데이터, 볼륨 할당. 3대로 Raft 리더 선출
Volume 8080 실제 파일 데이터(청크) 저장
Filer 8888 파일 메타데이터와 REST API
S3 Gateway 8333 S3 호환 API (Filer와 별도 프로세스)

노드마다 같은 weed 버전을 설치한다. Master는 노드마다 -ip만 자기 주소로 바꾸고 -peers에는 3대 전체를 모두 넣는다.

# seaweed-master.service (ExecStart)
/usr/local/bin/weed master \
  -ip=<NODE_IP> \
  -ip.bind=0.0.0.0 \
  -port=9333 \
  -mdir=/data/seaweedfs/master \
  -peers=<NODE1_IP>:9333,<NODE2_IP>:9333,<NODE3_IP>:9333
curl -s http://<NODE1_IP>:9333/cluster/status | grep -A2 Leader
# {"IsLeader":true,"Leader":"<NODE1_IP>:9333","Peers":[...]}

Volume은 Master 3대를 -mserver로 가리킨다.

# seaweed-volume.service (ExecStart)
/usr/local/bin/weed volume \
  -mserver=<NODE1_IP>:9333,<NODE2_IP>:9333,<NODE3_IP>:9333 \
  -ip=<NODE_IP> \
  -ip.bind=0.0.0.0 \
  -port=8080 \
  -dir=/data/seaweedfs/volume \
  -max=30000

Filer는 디렉터리 메타데이터를 저장할 스토어가 필요하다. 일부 버전에서는 -leveldb2.dir 옵션을 지원하지 않아 filer.toml로 스토어를 지정했다.

# /etc/seaweedfs/filer.toml
[filer]
store = "leveldb2"
port = 8888
ip = "0.0.0.0"
defaultReplication = "000"

[leveldb2]
enabled = true
dir = "/data/seaweedfs/filer/leveldb2"

Filer 유닛에서 걸린 점이 몇 가지 있다.

  • Filer는 실행할 때 WorkingDirectory에서 filer.toml을 찾는다. /etc/seaweedfs/와 WorkingDirectory(/data/seaweedfs/filer) 둘 다에 파일을 두고, 유닛에는 WorkingDirectory=를 반드시 넣는다.
  • 내 메모에는 [leveldb2]에 enabled = true가 없으면 Filer가 스토어를 인식하지 못해 exit 255로 종료된다고 적어 뒀다.
  • 옵션은 한 줄에 붙여 쓴다. \로 줄을 나눈 뒤 -s3를 따로 두면 systemd가 "Missing =" 경고를 낼 수 있다.

S3는 Filer 옵션이 아니라 별도 프로세스(weed s3)로 띄웠다. 기본값이 -ip.bind=localhost라서 -ip.bind=0.0.0.0을 꼭 줘야 밖에서 8333에 접속된다.

# seaweed-s3.service
[Unit]
After=network.target seaweed-filer.service
Wants=seaweed-filer.service

[Service]
ExecStart=/usr/local/bin/weed s3 \
  -filer=127.0.0.1:8888 \
  -port=8333 \
  -ip.bind=0.0.0.0 \
  -config=/etc/seaweedfs/s3-config.json

인증은 s3-config.json(identities의 accessKey, secretKey, actions)을 노드 3대에 같은 내용으로 두고 -config로 지정한다. 파일을 고친 뒤에는 seaweed-s3를 재시작한다. 외부 클라이언트가 접속하려면 노드마다 8333, 8888, 9333 포트를 방화벽에서 열어 둔다.

9. Kubernetes 안에 올리기: Helm All-in-One

SeaweedFS를 VM이 아니라 Kubernetes 안에 올려 Thanos와 Loki의 S3 백엔드로 쓰기도 했다. MinIO를 SeaweedFS로 바꾼 구성이다. 차트는 seaweedfs/seaweedfs 4.0.405, 이미지 태그는 4.05였다.

helm repo add seaweedfs https://chrislusf.github.io/seaweedfs/
helm repo update
helm pull seaweedfs/seaweedfs --version 4.0.405 --untar

values.yaml은 All-in-One 모드와 S3 Gateway를 켜고, NodePort와 RWX 스토리지를 지정했다.

global:
  replicationPlacement: "000"
image:
  registry: "docker.io"
  repository: "chrislusf"
  tag: "4.05"

allInOne:
  enabled: true
  replicas: 1
  idleTimeout: 30
  metricsPort: 9324
  extraArgs:
    - "-volumeSizeLimitMB=10000"
    - "-volume.max=256"
  updateStrategy:
    type: Recreate
  s3:
    enabled: true
    port: 8333
    enableAuth: true
    existingConfigSecret: "seaweedfs-s3-config"
    createBuckets:
      - name: thanos-metrics
  sftp:
    enabled: false
  service:
    type: NodePort
    internalTrafficPolicy: Cluster
    nodePorts:
      filer: 30888
      s3: 30333
  data:
    type: "persistentVolumeClaim"
    claimName: seaweedfs-data-pvc
    size: 50Gi
    storageClass: <RWX_STORAGE_CLASS>
    accessModes: ["ReadWriteMany"]

S3 인증은 seaweedfs-s3-config Secret으로 넣는다. 형식은 앞의 s3.conf와 같다.

apiVersion: v1
kind: Secret
metadata:
  name: seaweedfs-s3-config
stringData:
  seaweedfs_s3_config: |
    {
      "identities": [
        {
          "name": "admin",
          "credentials": [
            { "accessKey": "<CHANGE_ME>", "secretKey": "<CHANGE_ME>" }
          ],
          "actions": ["Admin", "Read", "Write"]
        }
      ]
    }

차트를 그대로 쓰면 안 되는 부분이 두 군데 있어 템플릿을 고쳤다.

  • 버킷 훅 제거. templates/shared/post-install-bucket-hook.yaml의 helm.sh/hook 어노테이션 세 줄(post-install,post-upgrade, hook-weight, hook-delete-policy)을 주석 처리했다. 버킷이 자동으로 삭제되는 것을 막으려는 조치다.
  • NodePort 지정. templates/all-in-one/all-in-one-service.yml의 Filer와 S3 포트에 nodePort를 추가했다. 값은 allInOne.service.nodePorts.filer, .s3에서 읽는다.
- name: "swfs-filer"
  port: {{ .Values.filer.port }}
  targetPort: {{ .Values.filer.port }}
  {{- if eq .Values.allInOne.service.type "NodePort" }}
  nodePort: {{ .Values.allInOne.service.nodePorts.filer }}
  {{- end }}
  protocol: TCP

NodePort는 HAProxy로 TCP 프록시해서 접근했다.

listen seaweedfs-console
    bind *:30888
    mode tcp
    server master-1 <NODE_IP>:30888 check inter 2000 rise 2 fall 5

listen seaweedfs-s3
    bind *:30333
    mode tcp
    server master-1 <NODE_IP>:30333 check inter 2000 rise 2 fall 5

클라이언트 쪽 변경은 Thanos와 Loki에서 했다.

# Thanos objstoreConfig
type: s3
config:
  bucket: thanos-metrics
  endpoint: <NODE_IP>:30333
  access_key: <CHANGE_ME>
  secret_key: <CHANGE_ME>
  insecure: true
  signature_version2: true
# Loki storageConfig
storageConfig:
  aws:
    bucketnames: k8s-loki
    endpoint: http://seaweedfs-all-in-one.monitoring.svc.cluster.local:8333
    access_key_id: <CHANGE_ME>
    secret_access_key: <CHANGE_ME>
    insecure: true
    s3forcepathstyle: true

MinIO 계정 문자열을 그대로 넣어서 Thanos storegateway가 The access key ID you provided does not exist in our records.로 CrashLoopBackOff에 빠졌을 때는 위 7장의 확인 절차를 따랐다. 로그가 Available keys: 0, Auth enabled: true였으므로 키가 등록되지 않은 것이었고, s3cmd로 같은 엔드포인트와 signature_v2 = True로 ls를 해 보면 버킷이 보이는지 바로 검증할 수 있다. Loki Compactor가 뜨지 않으면 Filer(30888)를 노드 3대 모두 바라보도록 HAProxy server 줄을 늘려 봤다.
