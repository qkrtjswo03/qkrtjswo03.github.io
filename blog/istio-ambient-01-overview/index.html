Istio Ambient Mesh 개요: 사이드카 없이 ztunnel과 waypoint로 메시 만들기

핵심 결론
Ambient는 노드마다 ztunnel이 L4(mTLS)를 맡고, L7이 필요한 네임스페이스에만 waypoint proxy를 얹는다. 메시 편입은 네임스페이스 라벨 하나이고 Pod를 재시작하지 않는다.

사이드카 방식 Istio를 쓰면 Pod마다 Envoy가 하나씩 붙는다. 그 비용과 운영 부담을 줄이려고 나온 Ambient Mesh를 살펴봤다. 이 글은 개념과 구성 요소, 트래픽이 어떻게 흘러 들어가는지를 정리한 첫 글이다. 설치와 실습은 kind 실습과 Helm 설치에 있다.

Ambient Mesh란

Ambient Mesh는 기존 Sidecar 기반 Istio를 대체하는 새 아키텍처다. Pod 사이 보안(mTLS), 트래픽 관리, 원격 측정(telemetry)을 그대로 제공하면서 Sidecar 없이 동작한다. 기존에는 애플리케이션 Pod마다 Envoy Sidecar를 주입해야 했지만, Ambient에서는 노드마다 배포된 ztunnel이 Pod의 트래픽을 대신 처리한다.

장점은 네 가지로 정리된다.

  1. Sidecar 없이 메시 기능 제공: 애플리케이션 코드나 Pod 설정을 바꾸지 않고, 기존 서비스에 영향 없이 점진적으로 도입할 수 있다.
  2. 리소스 사용량 절감: Sidecar 방식은 Pod마다 Envoy가 CPU와 메모리를 따로 쓴다. Ambient는 L4를 ztunnel이, L7을 waypoint proxy가 맡아 전체 사용량이 줄어든다.
  3. L7 기능의 점진적 도입: 기본은 ztunnel이 L4(mTLS)만 처리하고, HTTP·gRPC 같은 L7 처리가 필요할 때 waypoint proxy를 추가한다.
  4. 운영 복잡성 감소: Pod마다 Sidecar를 관리하지 않아도 되고, 네임스페이스에 라벨만 붙이면 Pod 재시작 없이 적용된다.

구성 요소

Ambient를 처음 설치하면 istiod, istio-cni, ztunnel이 기본으로 올라오고, 이것만으로 L4 트래픽을 처리한다. L7을 처리하는 waypoint proxy는 별도로 구성해야 한다.

구성 요소 배포 형태 역할
istiod Deployment 컨트롤 플레인. 서비스 디스커버리, 정책 관리, mTLS 인증서 발급·갱신, Gateway 리소스로 waypoint 구성·관리
istio-cni DaemonSet (노드당 1개) 기존 CNI 플러그인의 확장. Ambient에 속한 Pod를 식별하고 그 Pod의 트래픽을 ztunnel로 리다이렉션하도록 구성
ztunnel (Zero Trust tunnel) DaemonSet (노드당 1개) L4 트래픽 처리. mTLS 암호화, L4 인증, 원격 측정. HBONE 프로토콜 사용
waypoint proxy Deployment (네임스페이스당 1개) L7 트래픽 처리. Envoy 기반이라 Sidecar와 같은 엔진이지만 애플리케이션과 독립적으로 구성·스케일. L7 인증과 원격 측정

HBONE

ztunnel은 HBONE(HTTP-Based Overlay Network Environment)으로 보안 트래픽을 주고받는다. 내부적으로는 HTTP/2 CONNECT를 이용해 mTLS를 적용한다. 자세한 구조는 Istio 공식 문서의 HBONE 설명에 나와 있다.

트래픽이 ztunnel로 들어가는 과정

istio-cni는 Pod 생성·삭제 같은 CNI 이벤트와, Kubernetes API 서버로 전해지는 Pod·네임스페이스 라벨 변경 이벤트를 지켜본다. Ambient에 속한 workload Pod가 생기면 다음 순서로 진행된다.

  1. istio-cni가 그 Pod를 드나드는 패킷을 ztunnel의 리스닝 포트(15008, 15006, 15001)로 리다이렉션하도록 규칙을 구성한다.
  2. ztunnel에게 Pod의 network namespace 안에 프록시 리스닝 포트를 만들어야 한다고 알린다.
  3. ztunnel이 새로 편입된 Pod를 위한 논리 프록시 인스턴스와 리스닝 포트를 만든다.
  4. 리다이렉션 규칙과 리스닝 포트가 준비되면 Pod가 메시에 들어오고 트래픽이 ztunnel을 통해 흐른다.

중요한 점은 이 리다이렉션이 호스트(노드) 영역이 아니라 Pod 내부에서 일어난다는 것이다. 자세한 그림은 공식 문서의 트래픽 리다이렉션 페이지에 있다.

수신과 송신

수신: HBONE(15008) 도착 → ztunnel이 decap → workload 포트로 전달
송신: workload의 outbound 트래픽 → ztunnel이 encap → HBONE으로 Pod 밖으로 전송
